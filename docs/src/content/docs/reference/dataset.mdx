`DataSet` manifests describe derived tables built using SQL or [PRQL](https://prql-lang.org) (Pipelined Relational Query Language).
Datasets typically select from `DataSource` views and may depend on other datasets.

## Spec overview

```yaml
apiVersion: bino.bi/v1alpha1
kind: DataSet
metadata:
  name: sales_summary
spec:
  query: |
    SELECT ...
  dependencies:
    - sales_csv
    - exchange_rates
```

Fields:

- `spec.query` – SQL query, either inline or loaded from an external file. Required if `spec.prql` and `spec.source` are not set.
- `spec.prql` – [PRQL](https://prql-lang.org) query, either inline or loaded from an external file. When set, takes precedence over `spec.query`. The PRQL is sent directly to the query engine which compiles it via the [prql extension](https://duckdb.org/community_extensions/extensions/prql).
- `spec.source` – direct pass-through to a DataSource without transformation. Mutually exclusive with `query` and `prql`.
- `spec.dependencies` – optional list of datasource references. Can be string names or [inline DataSource definitions](#inline-dataset-definitions). Inline definitions are referenced via `@inline(N)` syntax in queries.

## External query files

For complex queries, you can store them in separate `.sql` or `.prql` files and reference them using the `$file` syntax. This keeps your YAML manifests clean and enables syntax highlighting in your editor.

### Loading SQL from an external file

```yaml
apiVersion: bino.bi/v1alpha1
kind: DataSet
metadata:
  name: sales_summary
spec:
  query:
    $file: ./queries/sales_summary.sql
  dependencies:
    - sales_csv
```

### Loading PRQL from an external file

```yaml
apiVersion: bino.bi/v1alpha1
kind: DataSet
metadata:
  name: customer_orders
spec:
  prql:
    $file: ./queries/customer_orders.prql
  dependencies:
    - orders
    - customers
```

### File path resolution

- Paths are resolved relative to the manifest file containing the `$file` reference
- Both `./relative/path.sql` and `relative/path.sql` formats are supported
- Absolute paths are also supported but not recommended for portability

### Auto-reload and caching

External query files are fully integrated with bino's caching and hot-reload system:

- **Cache invalidation**: When an external SQL or PRQL file changes, the dataset cache is automatically invalidated
- **Hot-reload in preview**: Changes to external query files trigger automatic refresh in `bino preview` mode
- **Dependency graph**: External files appear in `bino graph` output for visibility

### Organizing query files

A recommended project structure for external queries:

```
my-report/
├── bino.toml
├── manifests/
│   ├── datasources.yaml
│   └── datasets.yaml
├── queries/
│   ├── sales_by_region.sql
│   ├── monthly_revenue.sql
│   └── customer_analysis.prql
└── data/
    └── sales.csv
```

## Simple aggregation

```yaml
---
apiVersion: bino.bi/v1alpha1
kind: DataSource
metadata:
  name: sales_csv
spec:
  type: csv
  path: ./data/sales.csv
---
apiVersion: bino.bi/v1alpha1
kind: DataSet
metadata:
  name: sales_by_region
spec:
  query: |
    SELECT
      region,
      SUM(amount) AS total_amount
    FROM sales_csv
    GROUP BY region
  dependencies:
    - sales_csv
```

## Dataset depending on multiple inputs

```yaml
---
apiVersion: bino.bi/v1alpha1
kind: DataSource
metadata:
  name: sales_fact
spec:
  type: parquet
  path: ./warehouse/fact_sales/*.parquet
---
apiVersion: bino.bi/v1alpha1
kind: DataSource
metadata:
  name: currency_rates
spec:
  type: csv
  path: ./data/currency_rates.csv
---
apiVersion: bino.bi/v1alpha1
kind: DataSet
metadata:
  name: revenue_eur
spec:
  query: |
    SELECT
      f.region,
      f.booking_date,
      f.amount * r.rate_to_eur AS revenue_eur
    FROM sales_fact f
    JOIN currency_rates r
      ON r.currency = f.currency
     AND r.valid_on = f.booking_date;
  dependencies:
    - sales_fact
    - currency_rates
```

Datasets are referenced from layouts via their `metadata.name` using the `dataset` field of charts, tables, and text components.

## Using PRQL

[PRQL](https://prql-lang.org) is a modern language for transforming data that compiles to SQL. It offers a more readable, pipeline-based syntax compared to traditional SQL.

When you specify `spec.prql`, bino automatically loads the [PRQL extension](https://duckdb.org/community_extensions/extensions/prql) and sends your PRQL query directly to the query engine for compilation and execution.

### Simple PRQL example

```yaml
---
apiVersion: bino.bi/v1alpha1
kind: DataSource
metadata:
  name: sales_csv
spec:
  type: csv
  path: ./data/sales.csv
---
apiVersion: bino.bi/v1alpha1
kind: DataSet
metadata:
  name: sales_by_region
spec:
  prql: |
    from sales_csv
    filter amount > 0
    group {region} (
      aggregate {
        total_amount = sum amount,
        order_count = count this
      }
    )
    sort {-total_amount}
  dependencies:
    - sales_csv
```

### PRQL with joins and transformations

```yaml
---
apiVersion: bino.bi/v1alpha1
kind: DataSource
metadata:
  name: orders
spec:
  type: csv
  path: ./data/orders.csv
---
apiVersion: bino.bi/v1alpha1
kind: DataSource
metadata:
  name: customers
spec:
  type: csv
  path: ./data/customers.csv
---
apiVersion: bino.bi/v1alpha1
kind: DataSet
metadata:
  name: customer_orders
spec:
  prql: |
    from orders
    join customers (==customer_id)
    derive full_name = f"{customers.first_name} {customers.last_name}"
    select {
      order_id,
      full_name,
      order_date,
      total
    }
    sort {-order_date}
    take 100
  dependencies:
    - orders
    - customers
```

For more PRQL syntax and examples, see the [PRQL documentation](https://prql-lang.org/book/).

## Row filtering

`spec.filter` declares a row filter that bino compiles to a SQL `WHERE` clause and applies server-side, before the rows reach the dataset cache or any component. It is a declarative alternative to writing the `WHERE` yourself, and it works on top of `query`, `source`, or inline dependencies alike.

A filter is a **group**: a logical operator (`and` or `or`) plus a list of `conditions`. Each condition is either a leaf (a `column`/`op`/`value` test) or another nested group, so you can express arbitrary boolean trees.

```yaml
spec:
  filter:
    op: and                       # and (default) | or
    conditions:
      - { column: region, op: in, value: [EMEA, APAC] }
      - { column: sales, op: gte, value: 1000 }
      - op: or                    # nested group
        conditions:
          - { column: product, op: regex, value: "^A" }
          - { column: product, op: notIn, value: [X, Y] }
```

`op` on a group defaults to `and` when omitted. Groups nest to any depth; each level is parenthesized in the generated SQL, so the example above compiles to `WHERE (region IN (?, ?) AND sales >= ? AND (regexp_matches(product, ?) OR product NOT IN (?, ?)))`.

### Filter operators

| Operator   | SQL                | `value` shape                                                              |
| :--------- | :----------------- | :------------------------------------------------------------------------- |
| `equal`    | `= ?`              | Scalar (string, number, boolean). A `null` value becomes `IS NULL`.        |
| `notEqual` | `<> ?`             | Scalar. A `null` value becomes `IS NOT NULL`.                              |
| `gt`       | `> ?`              | Scalar.                                                                    |
| `gte`      | `>= ?`             | Scalar.                                                                    |
| `lt`       | `< ?`              | Scalar.                                                                    |
| `lte`      | `<= ?`             | Scalar.                                                                    |
| `in`       | `IN (?, …)`        | Array of scalars. An empty array matches no rows. `null` elements are rejected. |
| `notIn`    | `NOT IN (?, …)`    | Array of scalars. An empty array matches all rows. `null` elements are rejected. |
| `regex`    | `regexp_matches()` | String only (a regular expression).                                        |

Column names are quoted as SQL identifiers and every `value` is passed as a bound parameter, so filter values never need escaping and are not a SQL-injection surface.

## Server-side aggregation

`spec.groupBy` declares a server-side SQL `GROUP BY`. bino wraps your query, groups by the listed `columns`, and projects the `aggregates` you request. This runs in DuckDB at build time, **upstream** of any component.

```yaml
spec:
  query: SELECT region, year, amount, sku FROM raw
  groupBy:
    columns: [region]
    aggregates:
      - { column: sales, fn: sum, as: total }
      - { column: sku, fn: countDistinct, as: skus }
```

- `columns` – one or more grouping columns. These appear in the output as-is.
- `aggregates` – the aggregated columns. Each needs a `column`, an `fn`, and an output name `as`. The `as` names must be unique and must not collide with a grouping column.

### Aggregate functions

| Function        | SQL                       |
| :-------------- | :------------------------ |
| `sum`           | `sum(col)`                |
| `avg`           | `avg(col)`                |
| `min`           | `min(col)`                |
| `max`           | `max(col)`                |
| `count`         | `count(col)` (or `count(*)` when `column` is omitted or `*`) |
| `countDistinct` | `count(DISTINCT col)`     |
| `first`         | `first(col)`              |
| `last`          | `last(col)`               |

`first` and `last` accept an optional `orderBy` (and `orderDesc: true`) to make the pick deterministic — without it, which row wins is undefined:

```yaml
aggregates:
  - { column: status, fn: last, as: latest_status, orderBy: updated_at, orderDesc: true }
```

**`groupBy` collapses rows.** This is a true SQL `GROUP BY`: the output has exactly one row per distinct combination of `columns`, and any column that is neither grouped nor aggregated is dropped. This is a different mechanism from the [Table](/reference/table/) component's render-time roll-up, which groups the rows it is given in the browser for display. `groupBy` pre-aggregates the data itself; the two are independent and can be combined.

## Computed index columns

`spec.indexColumns` adds derived columns to the output — typically the `*Index` order columns (`categoryIndex`, `rowGroupIndex`, `subCategoryIndex`, `columnGroupIndex`) described under [Standard Dataset Schema](#standard-dataset-schema). bino computes each as a SQL expression projected over the (optionally filtered and grouped) result.

This is the **supported way to satisfy the `category` → `categoryIndex` pairing rule** (and its `rowGroup` / `subCategory` / `columnGroup` siblings) **without hand-writing the SQL**. The [Dependent required](#validation-checks) validation insists that whenever you emit a grouping dimension you also emit its index; an `indexColumn` produces that index for you.

```yaml
spec:
  indexColumns:
    - { column: categoryIndex, fn: denseRank, over: region }     # dense_rank() OVER (ORDER BY region)
    - { column: rowGroupIndex, fn: hash, of: region }            # hash(region)
    - { column: subCategoryIndex, expr: "row_number() OVER ()" } # raw escape hatch
```

Each entry has a `column` (the output name) and exactly one of:

- **`fn: hash`** with `of: <column>` — a stable-per-value bucket via DuckDB's `hash()`. Good for turning a text dimension into a numeric index where you only need distinct values to sort together, not a specific order.
- **`fn: rowNumber` / `rank` / `denseRank`** with `over: <column>` — a window function ordered by `over`. Add `overDesc: true` to reverse, and `partition: [<column>, …]` to restart the numbering per partition. This is the usual choice for `categoryIndex` and friends, where you want 1, 2, 3, … in a meaningful order.
- **`expr: <SQL>`** — a raw SQL expression, the escape hatch for anything the helpers don't cover (multi-column ordering, arithmetic, `CASE`, …). Mutually exclusive with `fn`.

Index expressions can reference any column of the underlying result, including grouped columns and aggregate aliases, but they cannot reference each other.

## Gotchas and limits

- **PRQL is not supported with these transforms in v1.** `filter`, `groupBy`, and `indexColumns` require a SQL `query` or `source`. A `prql` query combined with any of the three is rejected at build time — express the equivalent filtering/grouping in PRQL itself, or switch the dataset to SQL.
- **`groupBy` collapses rows.** As above, it is a real `GROUP BY` and discards ungrouped, unaggregated columns. If you only want display-time grouping and want to keep every column, leave `groupBy` off and group in the Table component instead.
- **`indexColumns.expr` is raw, author-trusted SQL.** It is interpolated into the generated query verbatim, exactly like `spec.query` and `spec.prql`. Only put trusted SQL there; it is not parameterized or sanitized. (`column`, `of`, `over`, and `partition` are identifier-quoted and safe.)
- **`hash` is not stable across DuckDB versions.** DuckDB's `hash()` makes no cross-version guarantee, so a `fn: hash` index column can change between bino releases that bump DuckDB. Use it where only grouping/ordering of like values matters, not where you persist or compare the index value over time.

## Standard Dataset Schema

To work correctly with visualization components like [Charts](/reference/chart-structure/) and [Tables](/reference/table/), your dataset queries should return rows that conform to the standard schema. While not all fields are required for every component, following this structure ensures proper aggregation, drill-down, and filtering behavior.

### Measure Values (Scenarios)

The schema supports four parallel sets of scenario columns for comparative analysis (e.g., Actual vs Plan).

| Column          | Description                                                   |
| :-------------- | :------------------------------------------------------------ |
| `ac1` ... `ac4` | **Actual** values (current measurements)                      |
| `pp1` ... `pp4` | **Previous Period** values (Year-over-Year, Month-over-Month) |
| `fc1` ... `fc4` | **Forecast** values (predictions)                             |
| `pl1` ... `pl4` | **Plan/Budget** values (targets)                              |

### Grouping Dimensions

These fields determine how data is hierarchically organized and sorted.

| Dimension     | Index Column       | Description                                                 |
| :------------ | :----------------- | :---------------------------------------------------------- |
| `rowGroup`    | `rowGroupIndex`    | Top-level row grouping (e.g., "Revenue", "Costs").          |
| `category`    | `categoryIndex`    | Primary data dimension (e.g., "Product A", "Region North"). |
| `subCategory` | `subCategoryIndex` | Detail dimension for drill-down (creates "thereOf" rows).   |
| `columnGroup` | `columnGroupIndex` | Column-level grouping for breaking down measures.           |

**Note**: When providing a grouping dimension string (e.g., `rowGroup`), you should likewise provide the corresponding index (e.g., `rowGroupIndex`) to ensure consistent sort ordering.

### Metadata & Control Fields

| Column      | Type     | Description                                                                                                                       |
| :---------- | :------- | :-------------------------------------------------------------------------------------------------------------------------------- |
| `date`      | `string` | **Required for TimeCharts**. ISO 8601 date (e.g., `2024-01-15`). Used for time-series axes and normalization.                     |
| `operation` | `string` | Aggregation sign: `'+'` (add) or `'-'` (subtract). Defaults to `'+'`. Useful for P&L structures where costs subtract from totals. |
| `setname`   | `string` | Dataset identifier. Used by some charts to distinguish multiple query results.                                                    |

### Example Query

Here is an example SQL query producing a compliant dataset:

```sql
SELECT
  'Revenue' as rowGroup,
  1 as rowGroupIndex,
  product_name as category,
  product_rank as categoryIndex,
  '2024-01-15' as date,
  sum(sales_amount) as ac1,
  sum(budget_amount) as pl1
FROM sales_data
GROUP BY product_name, product_rank
```

## Built-in SQL functions

bino registers a few scalar helper functions on the DuckDB engine, so they are available in every DataSet (and DataSource) query without any import or extension.

### `op(value)` — sign as an operator

`op` reduces a numeric value to its sign as a string — exactly the shape the `operation` control field (documented above) expects.

| Input       | Result                |
| :---------- | :-------------------- |
| `value > 0` | `'+'`                 |
| `value < 0` | `'-'`                 |
| `value = 0` | `''` (empty string)   |
| `NULL`      | `NULL`                |

It accepts any numeric type (INTEGER, BIGINT, DECIMAL, DOUBLE, …) and returns `VARCHAR`.

```sql
SELECT
  account_name    AS category,
  sum(amount)     AS ac1,
  op(sum(amount)) AS operation   -- '+' for revenue, '-' for costs
FROM ledger
GROUP BY account_name
```

### `iop(value)` — inverse sign

`iop` is the inverse of `op` (`+` becomes `-` and vice versa; `0` stays `''`). Use it for **inverted** measures, where an increase is unfavorable — costs, headcount, error rates, churn — so a rising value reads as a negative signal.

| Input       | `op`  | `iop` |
| :---------- | :---- | :---- |
| `value > 0` | `'+'` | `'-'` |
| `value < 0` | `'-'` | `'+'` |
| `value = 0` | `''`  | `''`  |

### Absolute value

There is no bino-specific helper for absolute values — DuckDB's built-in `abs()` already does it (`abs(-500)` → `500`). Combine it with `op` to render a signed magnitude as text:

```sql
SELECT op(variance) || abs(variance)::VARCHAR AS signed_variance
-- variance = -500  ->  '-500'
-- variance =  500  ->  '+500'
```

## Data Validation

bino can validate query results against the standard schema at build time. This catches common data issues early:

### Validation checks

| Check                     | Description                                                         |
| :------------------------ | :------------------------------------------------------------------ |
| Type validation           | String fields (`category`, `rowGroup`, etc.) must be strings        |
| Type validation           | Number fields (`ac1`, `categoryIndex`, etc.) must be numbers        |
| Enum validation           | `operation` must be `"+"` or `"-"`                                  |
| Date format               | `date` must be ISO 8601 format (`YYYY-MM-DD`)                       |
| Dependent required        | `rowGroup` requires `rowGroupIndex`, `category` requires `categoryIndex`, etc. |

### Enabling validation

Data validation is enabled by default in `warn` mode. Configure via CLI flags:

```bash
# Log warnings and continue (default)
bino build --data-validation=warn

# Treat validation errors as fatal
bino build --data-validation=fail

# Skip validation entirely
bino build --data-validation=off
```

For lint-only validation (without building), use `--execute-queries`:

```bash
bino lint --execute-queries
```

### Sample size

For efficiency, bino validates only the first N rows per dataset. Configure via environment variable:

```bash
BNR_DATA_VALIDATION_SAMPLE_SIZE=100 bino build
```

Default sample size is 10 rows.

## Conditional inclusion with constraints

DataSet documents support `metadata.constraints` to conditionally include them for specific artefacts, modes, or environments.

### Preview-only datasets

Include debug or diagnostic datasets only during development:

```yaml
apiVersion: bino.bi/v1alpha1
kind: DataSet
metadata:
  name: debug_metrics
  constraints:
    - mode==preview
spec:
  query: |
    SELECT * FROM raw_data LIMIT 100
  dependencies:
    - raw_data
```

### Format-specific datasets

Use different datasets for different output formats:

```yaml
# Detailed dataset for print (A4/Letter)
apiVersion: bino.bi/v1alpha1
kind: DataSet
metadata:
  name: sales_summary
  constraints:
    - spec.format in [a4,letter]
spec:
  query: |
    SELECT region, product, month, revenue, costs, margin
    FROM sales_fact
    GROUP BY region, product, month

---
# Summarized dataset for screen (XGA)
apiVersion: bino.bi/v1alpha1
kind: DataSet
metadata:
  name: sales_summary
  constraints:
    - field: spec.format
      operator: "=="
      value: xga
spec:
  query: |
    SELECT region, SUM(revenue) as total_revenue
    FROM sales_fact
    GROUP BY region
```

For the full constraint syntax and operators, see [Constraints and Scoped Names](/concepts/constraints-and-scoped-names/).

## Inline DataSet definitions

Instead of defining DataSets as separate documents, you can define them **inline** directly within components. This is useful for simple, component-specific data transformations.

### Inline DataSet in a Chart

```yaml
apiVersion: bino.bi/v1alpha1
kind: ChartStructure
metadata:
  name: sales_chart
spec:
  dataset:
    query: |
      SELECT region, SUM(amount) as total
      FROM sales_csv
      GROUP BY region
    dependencies:
      - sales_csv
  chartTitle: Sales by Region
  chartType: bar
  # ... chart configuration
```

### Inline DataSet with inline DataSource

You can nest inline DataSource definitions within an inline DataSet. Use the `@inline(N)` syntax to reference them by index:

```yaml
apiVersion: bino.bi/v1alpha1
kind: ChartStructure
metadata:
  name: quick_chart
spec:
  dataset:
    dependencies:
      - type: csv
        path: ./data/sales.csv
    query: |
      SELECT region, SUM(amount) as total
      FROM @inline(0)
      GROUP BY region
  chartTitle: Sales Overview
  # ... chart configuration
```

The `@inline(0)` reference points to the first item in the `dependencies` array (0-indexed). When you have multiple inline DataSources:

```yaml
spec:
  dataset:
    dependencies:
      - type: csv
        path: ./data/orders.csv
      - type: csv
        path: ./data/customers.csv
    query: |
      SELECT c.name, COUNT(*) as order_count
      FROM @inline(0) o
      JOIN @inline(1) c ON o.customer_id = c.id
      GROUP BY c.name
```

### Mixing inline and named references

You can mix inline DataSource definitions with named references:

```yaml
spec:
  dataset:
    dependencies:
      - sales_csv # Named reference to existing DataSource
      - type: csv # Inline definition
        path: ./data/rates.csv
    query: |
      SELECT s.*, r.rate
      FROM sales_csv s
      JOIN @inline(1) r ON s.currency = r.code
```

Note: Named references use their document name directly in SQL, while inline definitions use `@inline(N)`.

## Direct source pass-through

For simple cases where you want to use a DataSource directly without transformation, use the `source` field:

```yaml
apiVersion: bino.bi/v1alpha1
kind: DataSet
metadata:
  name: sales_passthrough
spec:
  source: sales_csv
```

This is equivalent to `SELECT * FROM sales_csv` but more explicit and efficient. The `source` field is **mutually exclusive** with `query` and `prql`.

### Inline source pass-through

You can also use inline DataSource definitions with `source`:

```yaml
apiVersion: bino.bi/v1alpha1
kind: Table
metadata:
  name: raw_data_table
spec:
  dataset:
    source:
      type: csv
      path: ./data/report.csv
  tableTitle: Raw Data
  # ... table configuration
```

## How inline definitions work

When bino processes inline definitions:

1. **Materialization**: Inline definitions are converted to synthetic documents during YAML loading
2. **Hash-based naming**: Generated documents get unique names like `_inline_datasource_a1b2c3d4`
3. **Deduplication**: Identical inline definitions share the same generated document
4. **Labels**: Generated documents have `bino.bi/generated: "true"` and `bino.bi/inline: "true"` labels

This means inline definitions are fully compatible with caching, the dependency graph, and all other bino features.

### Naming restrictions

User-defined document names must **not** start with `_inline_` as this prefix is reserved for generated inline definitions. The lint rule `inline-naming-conflict` enforces this.

## Attribute Reference

### Common Metadata

| Attribute | Type | Required | Default | Description |
|-----------|------|----------|---------|-------------|
| `apiVersion` | string | yes | — | Must be `bino.bi/v1alpha1`. |
| `kind` | string | yes | — | Must be `DataSet`. |
| `metadata.name` | string | yes | — | Unique identifier. Pattern: `^[A-Za-z0-9_]([-A-Za-z0-9_]*[A-Za-z0-9_])?$`. |
| `metadata.labels` | object | no | — | Key-value pairs for categorization and constraint matching. |
| `metadata.annotations` | object | no | — | Arbitrary key-value metadata, not used by the system. |
| `metadata.description` | string | no | — | Free-form description. |
| `metadata.constraints` | array | no | — | Conditional inclusion rules. See [Constraints](/concepts/constraints-and-scoped-names/). |

### Spec Attributes

Exactly one of `query`, `prql`, or `source` is required. They are mutually exclusive.

| Attribute | Type | Required | Default | Description | Sample |
|-----------|------|----------|---------|-------------|--------|
| `spec.query` | string or object | conditional | — | SQL query, inline or from external file. Required if `prql` and `source` are not set. | `query: SELECT * FROM sales` |
| `spec.prql` | string or object | conditional | — | PRQL query, inline or from external file. Required if `query` and `source` are not set. | `prql: from sales_csv` |
| `spec.source` | string or object | conditional | — | Direct DataSource pass-through. A string name or inline DataSource definition. Required if `query` and `prql` are not set. | `source: sales_csv` |
| `spec.dependencies` | array | no | — | List of DataSource references or inline definitions. Referenced in queries via `@inline(N)` syntax. | see below |

#### External file reference

```yaml
spec:
  query:
    $file: ./queries/sales_summary.sql
```

#### Dependencies with inline DataSources

```yaml
spec:
  dependencies:
    - sales_csv                    # named reference
    - type: csv                    # inline definition
      path: ./data/extra.csv
  query: |
    SELECT * FROM sales_csv
    UNION ALL
    SELECT * FROM @inline(1)
```
