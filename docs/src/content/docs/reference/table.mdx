`Table` manifests describe tables bound to datasets.
They control formatting, grouping, scenarios, and optional drilldown views.

## Minimal definition

The smallest well-formed `Table` sets the required `spec.dataset` plus the fields
that turn it into an IBCS table: the scenario columns, at least one variance
column, and row grouping. `measureType` and `measureUnit` label the numbers so
the reader knows what they mean.

```yaml
apiVersion: bino.bi/v1alpha1
kind: Table
metadata:
  name: revenue_table
spec:
  dataset: revenue_by_segment
  scenarios: ["ac1", "pp1"]
  variances: ["dac1_pp1_pos", "drac1_pp1_pos"]
  grouped: true
  measureType: currency
  measureUnit: "EUR"
```

All attributes are listed in the [Attribute Reference](#attribute-reference) below.

`dataset` accepts the dataset name shown above, an inline [`DataSet`](/reference/dataset/)
definition, or an array of both. `scenarios`, `variances`, `order`, and
`orderDirection` can also be taken from the surrounding layout instead of being
repeated here (see [Inherited props](#inherited-props)).

## Fields

- `dataset` - required dataset reference: a name, an inline [`DataSet`](/reference/dataset/) definition, or an array of those.
- `filter` - optional filter expression.
- `order` - sort keys as a comma list: a dimension, a scenario or a variance, see [Sorting](#sorting). Scenario keys must appear in `scenarios`. Default: `category`. `auto` uses the key suggested by the dataset instead: subCategory if the dataset has subCategory values, else category, else rowGroup. With subCategory values the category rows keep their dataset order and `orderDirection` has no effect on them; `thereof` drilldown rows are sorted by subCategory, in the opposite direction to `orderDirection`. With only category values, `auto` and an omitted `order` sort the same.
- `orderDirection` - sort direction (`asc` or `desc`).
- `measureScale`, `measureType`, `measureUnit` - control how measures are interpreted and displayed.
- `categoryWidth` - width of the category column (`w5`..`w50`, `inf`).
- `dataFormat`, `dataFormatDigitsDecimal`, `dataFormatDigitsPercent` - number formatting.
- `grouped`, `showGroupTitle` - group rows by `rowgroup` and optionally show group headers.
- `showMeasureScale` - toggle measure unit in table header.
- `limit` - maximum rows per group; extra rows are cumulated as REST.
- `type` - table type (`list`, `sum`, `opt`, `sumnototal`, `optnototal`). Only `sum` and `opt` render a grand-total row at the bottom of the table. In `opt` tables the variances of sum rows follow the operation sign of their rows (template engines before **v1.0.0-next.34** computed them without the sign).
- `sumTitle` - label of that grand-total row. It is **not** a title above the table: it is the text in the category cell of the total row. Since the other table types render no total row, they ignore the value. When empty, the row is labelled with the IBCS grand-total symbol ❖.
- `scenarios` - list of scenario measures, or `auto`. When set to `auto`, scenarios are detected from the dataset silently. When left blank (and variances are also blank), they are detected with a warning.
- `variances` - list of variance definitions of the form `d<scenarioB>_<scenarioA>_[pos|neg|neu|op|opinv]`. See [Variance sentiment](#variance-sentiment).
- `barColumns` - list of column names to render as inline IBCS-compliant bar charts instead of numbers.
- `barColumnWidth` - maximum width of inline bar/pin chart columns in em (`w5`..`w100`). Default: `w10`.
- `unitScaling` - data units displayed per 1 em of bar length for absolute variance bars (d\_ prefix columns) - map-scale semantics: a larger value means smaller bars. Also accepts `auto` (fit the largest bar to the bar column) or a [ScalingGroup](/reference/scaling-group/) name. Default: 100.
- `percentageScaling` - percentage points displayed per 1 em of pin length for relative variance pins (dr\_ prefix columns); `2` means a +2 % pin is 1 em long. Also accepts `auto` or a scaling group name. Default: 2.
- `scale` - proportional scaling of the entire table (font size, em-based spacing, SVG bar charts, pins, patterns). All visual dimensions scale together.
  - _not set_ - auto-scale to fit the parent width; emits an `AUTO_scale` warning with the applied factor. (An empty string `""` is rejected by the schema.)
  - `"none"` - no scaling; render at the base font size regardless of available space.
  - `"auto"` - auto-scale to fit the parent width silently (no warning).
  - A positive number (`"0.5"`, `"1.2"`, …) - fixed factor applied to the base font size.
- `thereof`, `partof`, `columnthereof` - drilldown configuration.
- `interval` - repeats the entire scenario/variance column block once per interval group, rendered under a spanning header band. Values: `none` (default), `setname`, or a date granularity (`year`, `quarter`, `month`, `week`, `day`, `hour`, `minute`, `second`, `millisecond`, `auto`). Mutually exclusive with `columnthereof` (`columnthereof` wins). See [Interval column grouping](#interval-column-grouping).
- `categoryIntervalPosition` - number of interval groups left of the category column. `0` (default) keeps the category column first. See [Position of the category column](#position-of-the-category-column).
- `runningSum` - with `grouped`, each group sum row holds the running result of all rows from the first group through its own group. No effect with `columnthereof`. See [Calculation schemes](#calculation-schemes).
- `thereofPosition` - where the `thereof` rows print: `below` (default) or `above` their parent. See [Calculation schemes](#calculation-schemes).
- `varianceWaterfall` - draws the absolute variance columns of `barColumns` as a waterfall down the rows. See [Variance waterfall](#variance-waterfall).
- `attributes` - computed attribute columns rendered between the category and scenario columns; ordered list of `{label, expression}` pairs. See [Computed attribute columns](#computed-attribute-columns).
- `i18nNamespace` - optional namespace consulted for this component's labels; missing keys fall back to `_system`. When unset, it is resolved from the nearest ancestor carrying one.
- `selectedStyle` - optional name of a [`ComponentStyle`](/reference/component-style/) to apply; merged over the `_system` and `_default` styles.
- `ruleset` - optional name of a [`RuleSet`](/reference/ruleset/) to apply, or `inherited-closest` / `inherited-page` to inherit the surrounding layout's rule set; merged over the `_system` and `_default` rule sets.

## Variance sentiment

The last part of a variance token says which direction is good. It picks the colour of the variance: green for good, red for bad.

| Suffix   | Meaning                                                                                                                                                                                                                                                  |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `_pos`   | More is better (revenue).                                                                                                                                                                                                                                |
| `_neg`   | More is worse (cost).                                                                                                                                                                                                                                    |
| `_neu`   | No good or bad direction. The variance is grey.                                                                                                                                                                                                         |
| `_op`    | The colour follows the contribution to the result. In a table with `type: opt` or `optnototal`, rows with operation `+` and sum rows act like `_pos`, rows with operation `-` act like `_neg`. A rising cost on a `-` row is red. `thereof` rows use the operation of their parent. In all other tables the values already carry the sign, so `_op` acts like `_pos`. |
| `_opinv` | The full inverse of `_op`. Use it for reports where the main measure is a cost.                                                                                                                                                                          |

The operation of a row comes from the `operation` column of the [dataset](/reference/dataset/) (`'+'` or `'-'`).

An income statement with one sentiment for all rows:

```yaml
---
apiVersion: bino.bi/v1alpha1
kind: Table
metadata:
  name: income_statement
spec:
  dataset: income_statement   # revenue rows with operation '+', cost rows with '-'
  type: opt
  sumTitle: "Net income"
  scenarios: ["ac1", "pl1"]
  variances: ["dac1_pl1_op", "drac1_pl1_op"]
```

Revenue above plan is green, cost above plan is red, and the net income row is green when it is above plan.

In an `opt` table the variances of the sum rows follow the operation sign of the rows they add up. Template engines before **v1.0.0-next.34** computed them without the sign.

`_op` and `_opinv` need template engine **v1.0.0-next.34** or newer. With an older engine `bino build` and `bino lint` stop with [`operation-sentiment-engine-version`](/appendix/lint-rules/#operation-sentiment-engine-version), and `bino preview` shows that error. A project without them keeps working on its engine.

## Sorting

`order` takes one sort key or a comma list of keys without spaces (`rowgroupindex,dac1_pp1`), applied from left to right with `orderDirection`. Scenario and variance keys are lowercase. A key is one of:

| Key                                                                                              | Sorts by                                                                                                       |
| ------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| `category`, `categoryindex`, `rowgroup`, `rowgroupindex`, `subcategory`, `subcategoryindex`      | The dimension column. Write it lowercase or in camelCase (`rowGroupIndex`).                                    |
| `ac1`-`ac4`, `fc1`-`fc4`, `pp1`-`pp4`, `pl1`-`pl4`                                               | The scenario. It must appear in `scenarios`.                                                                   |
| a variance like `dac1_pp1` or `drac1_pl1_pos`                                                    | The variance, written like its column. The sentiment suffix is allowed and has no effect on the sort.          |
| a scenario or variance with `@<setname>`, like `ac1@_November` or `dac1_pp1_pos@_November`        | The value in one block of `interval: setname`. Without `@` the sum over all blocks is used.                    |

```yaml
---
apiVersion: bino.bi/v1alpha1
kind: Table
metadata:
  name: biggest_misses
spec:
  dataset: revenue_by_month
  scenarios: ["ac1", "pp1"]
  variances: ["dac1_pp1_pos", "drac1_pp1_pos"]
  interval: setname
  grouped: true
  order: "dac1_pp1_pos@_November"   # largest drop against last year in November first
  orderDirection: asc
```

A variance key or a key with `@` sorts the rows inside their row groups. The groups keep their `rowGroupIndex` order. Rows are sorted by the value printed in the cell, so in an `opt` table a row sorts by its signed value. Rows without a value, and relative variances with a zero reference, go last in both directions. `limit` picks the top rows and the REST row by the same value. The sorted variance does not have to be a shown column; the sort arrow appears only when it is. `@` without `interval: setname`, or with a setname that is not in the data, gives a warning and does not sort.

Variance keys and `@` need template engine **v1.0.0-next.35** or newer. Older engines sort by `category` instead, without an error. So with an older engine `bino build` and `bino lint` stop with [`table-order-engine-version`](/appendix/lint-rules/#table-order-engine-version), and `bino preview` shows that error. A project without these keys keeps working on its engine.

`titleOrder` of a `LayoutPage` or `LayoutCard` accepts the same keys, because a table with `order: inherited-closest` or `inherited-page` takes it (see [Inherited props](#inherited-props)). The title itself only understands dimensions, scenarios and variances with a sentiment: for a variance without sentiment (`dac1_pp1`) or a key with `@` it shows an `order: invalid value(s)` warning. A `ChartStructure` that inherits such a `titleOrder` cannot sort by it and sorts by `category`; `bino lint` reports this with [`chart-order-inherits-measure`](/appendix/lint-rules/#chart-order-inherits-measure). So set variance and `@` keys in the table's own `order` where you can.

## Example: Grouped table with drilldown

```yaml
---
apiVersion: bino.bi/v1alpha1
kind: Table
metadata:
  name: revenue_grouped_table
spec:
  dataset: revenue_detail
  measureScale: M
  measureType: currency
  measureUnit: "EUR"
  grouped: true
  showGroupTitle: true
  categoryWidth: w25
  type: list
  limit: 5
  scenarios: ["ac1", "pp1"]
  variances: ["dac1_pp1_pos"]
  thereof:
    - rowGroup: "Revenue"
      category: "Applications"
      subCategory: "Applications-A"
  partof:
    - rowGroup: "Revenue"
      category: "Applications"
  columnthereof:
    - scenario: "ac1"
      name: "DE"
      subGroups: ["Berlin", "Hamburg"]
```

## Computed attribute columns

`attributes` adds custom columns computed from dataset fields, rendered between
the category column and the scenario columns. Each entry maps a column header
label to an aggregate expression evaluated over the dataset rows behind each
table row:

```yaml
---
apiVersion: bino.bi/v1alpha1
kind: Table
metadata:
  name: revenue_with_attributes
spec:
  dataset: revenue_by_region
  scenarios: ["ac1", "pp1"]
  grouped: true
  type: sum
  attributes:
    - label: "Verkaufsleiter"
      expression: "set(_leiter)"
    - label: "Umsatz gesamt"
      expression: "sum(ac1)"
```

The list order defines the column order. Alternatively, a raw JSON object
string can be used; its key order defines the column order:

```yaml
attributes: '{"Verkaufsleiter": "set(_leiter)", "Umsatz gesamt": "sum(ac1)"}'
```

### Expression functions

| Function                   | Result                                                |
| -------------------------- | ----------------------------------------------------- |
| `set(field)`               | All distinct values in the group, joined with `", "`. |
| `first(field)`             | Value of the first row in the group.                  |
| `last(field)`              | Value of the last row in the group.                   |
| `min(field)`, `max(field)` | Numeric minimum/maximum.                              |
| `avg(field)`, `sum(field)` | Numeric average/sum; respects the row operation sign. |
| `lit(value)`               | Constant value rendered in every row.                 |

Notes:

- Field arguments must be plain identifiers (`[A-Za-z_][A-Za-z0-9_]*`): standard
  dataset fields (e.g. `ac1`) or custom fields prefixed with `_` (e.g. `_leiter`).
  Custom fields pass through datasources and datasets as extra row columns.
  `lit` accepts any non-empty constant.
- Results of `min`, `max`, `avg`, and `sum` are formatted like scenario cells
  (measure scale and decimal digits); other functions render as-is.
- Cells stay blank on total and group-header rows (SUM, GROUP_SUM, GROUPHEAD,
  REST, PARTELEMENT). On `thereof` drill rows, aggregates are computed over the
  drilled subset.
- Invalid entries are ignored and produce a component warning. Duplicate labels
  collapse (the last one wins).
- Requires template engine `v1.0.0-alpha.15` or newer; older engines silently
  ignore the attribute.

## Inline bar chart columns

Render variance and scenario columns as inline IBCS-compliant bar charts using `barColumns`:

```yaml
---
apiVersion: bino.bi/v1alpha1
kind: Table
metadata:
  name: revenue_with_bars
spec:
  dataset: revenue_by_segment
  measureScale: M
  measureUnit: "EUR"
  scenarios: ["ac1", "pp1"]
  variances: ["dac1_pp1_pos", "drac1_pp1_pos"]
  barColumns: ["dac1_pp1_pos", "drac1_pp1_pos"]
  unitScaling: 50
  percentageScaling: 1
```

### Bar chart types

| Column prefix                      | Visualization                                                                            | Description                                                                                                      |
| ---------------------------------- | ---------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `d_` (absolute variance)           | Horizontal bar                                                                           | Bar extends left (negative) or right (positive) from the axis. The color comes from the sentiment (green good, red bad), the pattern from the minuend: AC and PY solid, FC hatched with an outline, PL outlined. |
| `dr_` (relative variance)          | Pin chart                                                                                | Thin line in the sentiment color from the axis with a square head. The head takes the look of the minuend: AC solid dark, PY solid gray, FC hatched, PL a white square with a dark outline. The label sits next to the head. With a fixed `percentageScaling`, a pin that does not fit is cut and ends in an arrow, with its label inside the pin; auto scaling fits the largest pin. |
| `ac`, `pp`, `fc`, `pl` (scenarios) | IBCS grayscale bars, or an IBCS waterfall when grouping structure is present (see below) | AC: dark gray solid, PP: light gray solid, FC: dark gray hatched, PL: dark gray outlined.                        |

The axis of variance bars and pins is drawn in the look of the reference scenario (the subtrahend): PY a thick gray line, AC a thick dark line, PL a double line, FC a dashed dark line. So `dac1_pp1` and `dac1_pl1` columns show at once which comparison they are. Bars start at the edge of the axis. This look needs template engine **v1.0.0-next.35** or newer. Older engines end a pin in a round dot.

### Example: Scenario columns as bar charts

```yaml
---
apiVersion: bino.bi/v1alpha1
kind: Table
metadata:
  name: scenario_bars
spec:
  dataset: quarterly_data
  scenarios: ["ac1", "pp1", "fc1"]
  barColumns: ["ac1", "pp1", "fc1"]
```

### Scenario columns as an IBCS waterfall

When a scenario column listed in `barColumns` appears on a table with grouping
structure (`type: sum`/`opt`, or `thereof`/`partof` drilldowns), it automatically
renders as an IBCS waterfall instead of plain grayscale bars: data rows cascade
from the running total and sum rows anchor at zero.

```yaml
---
apiVersion: bino.bi/v1alpha1
kind: Table
metadata:
  name: revenue_waterfall
spec:
  dataset: revenue_by_segment
  grouped: true
  type: sum
  sumTitle: "Revenue waterfall"
  scenarios: ["ac1"]
  barColumns: ["ac1"]
  thereof:
    - rowGroup: "Revenue"
      category: "Applications"
      subCategory: "Applications-A"
```

Notes:

- Waterfall columns auto-scale to fit `barColumnWidth`; `unitScaling` does not
  apply to them (it only affects `d_`-prefixed absolute variance bars).
- Not supported in combination with `interval` or `columnthereof` - scenario
  columns on tables using either of those fall back to plain grayscale bars.

## Interval column grouping

`interval` repeats the entire configured scenario/variance column block once
per interval group, rendered under a spanning header band (e.g.
`2023 | 2024 | 2025`, each with the same columns):

```yaml
---
apiVersion: bino.bi/v1alpha1
kind: Table
metadata:
  name: revenue_by_year
spec:
  dataset: revenue_by_year
  scenarios: ["ac1"]
  variances: ["dac1_pp1_pos"]
  barColumns: ["dac1_pp1_pos"]
  interval: year
```

Values:

| Value                                                                                | Behaviour                                                                                                                                                                       |
| ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `none` (default)                                                                     | Feature disabled.                                                                                                                                                               |
| `setname`                                                                            | Groups by the dataset's `setname` column (non-date comparison). Rows with a blank `setname` are grouped under a `-` bucket. Blocks are ordered by the `setnameIndex` column, or by first appearance in the data without it. |
| `year`, `quarter`, `month`, `week`, `day`, `hour`, `minute`, `second`, `millisecond` | Buckets rows by the dataset's `date` column at the given granularity.                                                                                                           |
| `auto`                                                                               | Detects the date granularity from the dataset's date span.                                                                                                                      |

`interval` and `columnthereof` are mutually exclusive; if both are set,
`columnthereof` wins and `interval` is ignored. A date-based `interval` on a
dataset with no date values is likewise ignored.

### Order of the setname groups

With `interval: setname` the optional dataset column `setnameIndex` sets the
order of the groups: ascending by `setnameIndex`. The order then does not
depend on the row order of the query. Example: three months, then a
year-to-date block.

```sql
SELECT 'Jan' AS setname, 0 AS setnameIndex, category, categoryIndex, ac1, pp1 FROM jan
UNION ALL
SELECT 'Feb', 1, category, categoryIndex, ac1, pp1 FROM feb
UNION ALL
SELECT 'Mar', 2, category, categoryIndex, ac1, pp1 FROM mar
UNION ALL
SELECT 'YTD', 3, category, categoryIndex, ac1, pp1 FROM ytd
```

- No row has a numeric `setnameIndex`: the groups keep the order of first
  appearance, as before.
- A `setname` with several different indexes uses the smallest one.
- Groups without an index come after the indexed groups, in order of first
  appearance. Groups with the same index keep the order of first appearance.
- `setnameIndex` has no effect on date intervals.

`setnameIndex` needs template engine **v1.0.0-next.39** or newer. Older engines
ignore the column and keep the order of first appearance, without an error.
Bino cannot check this, because the column is in the data: pin a new enough
`engine-version` in `bino.toml`.

### Position of the category column

`categoryIntervalPosition` is the number of interval groups that stand left of
the category column. The default `0` keeps the category column first.

```yaml
---
apiVersion: bino.bi/v1alpha1
kind: Table
metadata:
  name: revenue_by_month
spec:
  dataset: revenue_by_month
  scenarios: ["ac1", "pp1"]
  interval: setname
  categoryIntervalPosition: 3
```

With the four groups from above:

```text
categoryIntervalPosition: 0 (default)

| Category | Jan     | Feb     | Mar     | YTD     |
|          | AC | PP | AC | PP | AC | PP | AC | PP |

categoryIntervalPosition: 3

| Jan     | Feb     | Mar     | Category | YTD     |
| AC | PP | AC | PP | AC | PP |          | AC | PP |

categoryIntervalPosition: 4

| Jan     | Feb     | Mar     | YTD     | Category |
| AC | PP | AC | PP | AC | PP | AC | PP |          |
```

- A value equal to the number of groups puts the category column last. With 8
  groups, value 8 puts the category column last.
- The category column means the whole row header block: the category label
  together with the columns that belong to it. These are the operation column
  (the sign column of an `opt` table) and the
  [attribute columns](#computed-attribute-columns). The block moves as one unit
  in every row of the table.
- The value works with `interval: setname` and with the date intervals.
- A value larger than the number of groups is an error. The table shows a
  warning and puts the category column last. With `interval: setname` Bino
  reports it as
  [`table-category-interval-position-too-large`](/appendix/lint-rules/#table-category-interval-position-too-large).
- Without an active interval (`none`, not set, or `columnthereof` set) the
  value is ignored. Bino reports it as
  [`table-category-interval-position-unused`](/appendix/lint-rules/#table-category-interval-position-unused).

`categoryIntervalPosition` above 0 needs template engine **v1.0.0-next.39** or newer. Older engines keep the category column first, without an error. So with an older engine `bino build` and `bino lint` stop with [`table-category-interval-position-engine-version`](/appendix/lint-rules/#table-category-interval-position-engine-version), and `bino preview` shows that error.

## Calculation schemes

A calculation scheme is a table that walks from one result to the next, such as
an income statement: Sales revenue, Operating result, Result before tax, Net
income. Three fields build it. All three are off by default.

- `runningSum: true` - with `grouped: true`, each group sum row holds the
  running result of all rows from the first group through its own group. So the
  row group is the result stage, and its name is the label of the result row.
  Use it with `type: optnototal`. With `type: opt` the grand total row is still
  printed and repeats the last result, because `runningSum` does not drop it.
  The results add up in the order the groups are printed, so order the groups
  by `rowGroupIndex`. Together with `columnthereof` it has no effect.
- `thereofPosition: above` - the `thereof` rows print before their parent, in
  normal size, indented and without the thereof prefix. The parent row then
  looks like a subtotal. It keeps its operation sign and its positive value,
  for example `- Operating expenses 600.0`. With `below` (default) the rows
  print after their parent with the prefix.
- `varianceWaterfall: true` - see [Variance waterfall](#variance-waterfall).

### Example: Income statement

Write costs as positive values with operation `-`. The table subtracts them in
the result rows and prints them without a sign.

| rowGroup          | rowGroupIndex | category               | categoryIndex | subCategory        | operation | ac1 | pp1 |
| ----------------- | ------------- | ---------------------- | ------------- | ------------------ | --------- | --- | --- |
| Sales revenue     | 1             | Licences               | 1             |                    | +         | 600 | 550 |
| Sales revenue     | 1             | Consulting             | 2             |                    | +         | 400 | 380 |
| Operating result  | 2             | Other operating income | 3             |                    | +         | 40  | 30  |
| Operating result  | 2             | Operating expenses     | 4             | Material expenses  | -         | 250 | 240 |
| Operating result  | 2             | Operating expenses     | 4             | Personnel expenses | -         | 300 | 280 |
| Operating result  | 2             | Operating expenses     | 4             | Other expenses     | -         | 50  | 60  |
| Result before tax | 3             | Financial income       | 5             |                    | +         | 20  | 10  |
| Net income        | 4             | Income tax             | 6             |                    | -         | 110 | 95  |

```yaml
---
apiVersion: bino.bi/v1alpha1
kind: Table
metadata:
  name: income_statement
spec:
  dataset: income_statement
  measureType: currency
  measureUnit: "EUR"
  grouped: true
  showGroupTitle: false
  type: optnototal
  order: categoryindex
  runningSum: true
  thereof:
    - rowGroup: "Operating result"
      category: "Operating expenses"
  thereofPosition: above
  scenarios: ["ac1", "pp1"]
  variances: ["dac1_pp1_op"]
  barColumns: ["dac1_pp1_op"]
  varianceWaterfall: true
```

The rows of the table, with the running results:

```
                                   PY      AC    ΔPY
+ Licences                      550.0   600.0  +50.0
+ Consulting                    380.0   400.0  +20.0
= Sales revenue                 930.0 1,000.0  +70.0
+ Other operating income         30.0    40.0  +10.0
    Material expenses           240.0   250.0  +10.0
    Personnel expenses          280.0   300.0  +20.0
    Other expenses               60.0    50.0  -10.0
- Operating expenses            580.0   600.0  +20.0
= Operating result              380.0   440.0  +60.0
+ Financial income               10.0    20.0  +10.0
= Result before tax             390.0   460.0  +70.0
- Income tax                     95.0   110.0  +15.0
= Net income                    295.0   350.0  +55.0
```

The previous year column comes first. Operating result is
1,000.0 + 40.0 - 600.0 = 440.0 in AC: the sum of its own group plus the result
before it. Without `runningSum` the row would show only its own
group, -560.0.

### Variance waterfall

`varianceWaterfall: true` draws the absolute variance columns listed in
`barColumns` as a waterfall down the rows:

- Each bar starts where the bar of the row before ended. Connector lines join
  the bars.
- In `opt` and `optnototal` tables a row with operation `-` and a positive
  variance moves left, as a rising cost lowers the result. In the example above
  the +20.0 of Operating expenses moves left. In the other types the values
  already carry the sign, so the bar follows the printed variance.
- Sum rows are bars from the axis. They show the variance of the result so far.
- With `runningSum` the walk continues across the result rows, down to the last
  result. Without it every group restarts at the axis.

Notes:

- Relative variance columns (`dr` prefix) stay pins.
- The waterfall bars fit the bar column. `unitScaling` does not apply to them.
- Not available with `interval` or `columnthereof`. The table draws plain
  variance bars then.
- `barColumns` must list an absolute variance. Without one Bino reports
  [`table-variance-waterfall-unused`](/appendix/lint-rules/#table-variance-waterfall-unused).
- `thereofPosition: above` without a `thereof` list is reported as
  [`table-thereof-position-unused`](/appendix/lint-rules/#table-thereof-position-unused).

`runningSum: true`, `thereofPosition: above` and `varianceWaterfall: true` need template engine **v1.0.0-next.40** or newer. Older engines ignore them and render the plain table, without an error. So with an older engine `bino build` and `bino lint` stop with [`table-calculation-scheme-engine-version`](/appendix/lint-rules/#table-calculation-scheme-engine-version), and `bino preview` shows that error.

## Scaling

Use `scale` to shrink or grow the entire table proportionally.
Font size, em-based padding, border widths, SVG bar charts, pin lengths,
dot radii, and hatch patterns all scale together.

```yaml
---
apiVersion: bino.bi/v1alpha1
kind: Table
metadata:
  name: scaled_table
spec:
  dataset: revenue_by_segment
  scenarios: ["ac1", "pp1"]
  scale: auto # shrink to fit the available card width
```

### Scale modes

| Value           | Behaviour                                                                                  |
| --------------- | ------------------------------------------------------------------------------------------ |
| _not set_       | Auto-scale to fit the parent width. Emits an `AUTO_scale` warning with the applied factor. |
| `none`          | No scaling. The table renders at its base font size regardless of available space.         |
| `auto`          | Auto-scale to fit the parent width silently (no warning).                                  |
| `0.5`, `1.2`, … | Fixed factor applied to the base font size. All dimensions scale proportionally.           |

`scale` only fits the width. A table whose content is taller than the space it
gets is clipped at the bottom by the page cell - the last rows, grand total
included, simply are not drawn. From template engine **v1.0.0-next.26** on the
engine reports this as a diagnostic: the error `ERR_overflow` when `scale` fixes
the size, the warning `WARN_overflow` when the engine chose it (engines before
**v1.0.0-next.29** use `WARN_overflow` for both). A build with
[`--layout-state`](/cli/layout-state/) prints it as a `layout-overflow` finding,
and the preview inspector shows it on the component.

What helps: give the table more space (fewer components on the page, a taller
layout), show fewer rows (`limit`), or set a smaller fixed `scale`. Setting
`scale: auto` does not help - it fits the width, not the height.

## Inherited props

Instead of repeating `scenarios`, `variances`, `order`, and `orderDirection` on every component, you can inherit them from an ancestor `LayoutPage` or `LayoutCard`. Set any of these fields to a special keyword:

| Value               | Resolves from                                                     |
| ------------------- | ----------------------------------------------------------------- |
| `inherited-closest` | Nearest ancestor `LayoutCard` or `LayoutPage` that sets the field |
| `inherited-page`    | Nearest ancestor `LayoutPage` only (skips cards)                  |

The inherited value is read from the ancestor's corresponding `titleScenarios`, `titleVariances`, `titleOrder`, or `titleOrderDirection` field. With `inherited-closest`, a `LayoutCard` that does not set the field is skipped and the lookup continues outwards to the `LayoutPage`. Template engines before **v1.0.0-next.28** ask only the nearest card or page.

A keyword cannot be resolved when the page (and, for `inherited-closest`, every enclosing card) does not set the matching field. From template engine **v1.0.0-next.28** on, the component then behaves as if the field were not set (scenarios are auto-detected, the default order is used) and shows a warning. Older engines keep the keyword as a literal value: nothing is auto-detected and the component renders without usable scenarios or order. `bino lint` reports this case with the rule [`inherited-prop-unresolved`](/appendix/lint-rules/#inherited-prop-unresolved).

```yaml
children:
  - kind: Table
    spec:
      dataset: revenue_data
      grouped: true
      type: sum
      scenarios: inherited-page # uses page's titleScenarios
      variances: inherited-page # uses page's titleVariances
```

See the [ChartStructure inherited props](/reference/chart-structure/#inherited-props) section for full examples.
