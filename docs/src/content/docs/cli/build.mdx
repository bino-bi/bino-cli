title: bino build
description: Validate manifests, execute datasets, and export PDFs.
---

`bino build` is the main command for producing PDFs from your report bundle.
It validates manifests, runs SQL in the embedded query engine, and renders PDFs via the rendering engine.

## Usage

```bash
bino build [flags]
```

Common flags:

- `--work-dir` - report bundle directory (default: `.`).
- `--out-dir` - output directory relative to workdir (default: `dist`).
- `--artefact` - build only specified artefact names (can be repeated).
- `--exclude-artefact` - skip specified artefact names (can be repeated).
- `--chrome-path` - path to a Chrome or Chromium binary (default: auto-detected from cache or `CHROME_PATH` env).
- `--no-graph` - skip writing dependency graph files.
- `--no-lint` - skip running lint rules (lint runs by default).
- `--log-sql` - log executed SQL queries.
- `--layout-state` - write `<artefact>.layout.json` describing the rendered report and report render issues (empty components, overflow, diverging scales) as build warnings. Without it a build reports only content that is lost: cut off (`layout-overflow`) or not drawn because of an error (`layout-component-error`), one line per component. See [Layout State](/cli/layout-state/).
- `--data-validation` - data validation mode: `warn` (default), `fail`, or `off`. See [Data Validation](#data-validation).
- `--warn-on-query-errors` - downgrade a failed dataset query to a warning and render the report with the remaining data. By default a failed query fails the build.
- `--screenshot` - write a PNG of a report, page or component to `<out-dir>/screenshots/`, with no `ScreenshotArtefact` needed (can be repeated). See [Screenshots](#screenshots).
- `--screenshot-scale` - device scale factor for `--screenshot`: `1` (default) or `2` for twice the pixels.
- `--overlay` - build with the files of a directory on top of the project, for this run only. See [Overlay](#overlay).
- `--number-values` - write `<artefact>.values.json` with every number each table and chart shows. See [Number values](#number-values).
- `--verify-numbers` - check those numbers against the DataSet rows (implies `--number-values`). See [Checking the numbers](#checking-the-numbers).

Build log flags:

- `--build-log-format` - build log file format: `text` (default) or `json`.
- `--log-format` - terminal logging format: `text` (default) or `json` (one JSON object per line). With `json`, a failed build writes its error as a JSON line too, with `file`, `line` and `column` when the error comes from a manifest, and each built PDF is logged with its `artefact` name and `path`.
- `--embed-data-csv` - embed CSV data previews in JSON log.
- `--embed-data-max-rows` - maximum rows to embed per query (default: `10`).
- `--embed-data-max-bytes` - maximum bytes per embedded CSV (default: `65536`).
- `--embed-data-base64` - base64 encode embedded CSV data (default: `true`).
- `--embed-data-redact` - redact sensitive columns in embedded data (default: `true`).
- `--detailed-execution-plan` - include step-by-step timing.

See [Build Logs](/cli/build-logs/) for full documentation on JSON logs, CSV embedding, and execution plan tracking.

## Screenshots

`--screenshot` renders PNGs of the project without a `ScreenshotArtefact` manifest. Nothing is
written to your manifests. Each value is one of:

| Value                     | Captures                                                                                                                                             | File in `<out-dir>/screenshots/`                            |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| `ReportArtefact/<name>`   | Every page of the report, as in its PDF.                                                                                                             | `reportartefact-<name>-001.png`, `-002.png`, ...            |
| `LayoutPage/<name>`       | One page, rendered in the first `ReportArtefact` (by name) that lists it, so it has that report's format, language and style. A page that no report lists is rendered alone with its own `pageFormat`. | `layoutpage-<name>.png` (numbered if the page renders more than once, for example with params) |
| `<ComponentKind>/<name>`  | One component, such as `ChartStructure/revenue`, rendered on its page in the first `ReportArtefact` that lists the page and keeps the component after its constraints. Name a child by its `ref`, or by its `metadata.name`. A component inside a `Tree` is named by its `ref`. A standalone component that is on no page is rendered the way a [`ScreenshotArtefact`](/reference/screenshot-artefact/) renders it. | `<kind>-<name>.png`, kind in lower case                     |
| `<name>`                  | The `LayoutPage` with that name, or else the `ReportArtefact`. A name that is both fails; write the kind.                                            | as above                                                    |

Names are percent-encoded in file names, so `Text/@acme/kit/note` becomes `text-@acme%2Fkit%2Fnote.png`.
A value that names nothing fails the build with exit code 1 and lists every value that would work.

Without `--artefact`, a build with `--screenshot` produces only the screenshots: no PDF, no
`ScreenshotArtefact`, no `DocumentArtefact`. An `artefact` list in `bino.toml` does not change this.
Pass `--artefact` to build those artefacts in the same run.

With `--layout-state`, each value also writes `<file>.layout.json` next to its PNGs. Render issues
are reported as build warnings in both cases, as for a PDF.

With `--build-log-format json`, the build log lists every PNG in `screenshots`. `page` is set when a
value captures more than one page, and `layout_page` names the page shown:

```json
"screenshots": [
  {
    "ref": "ReportArtefact/sales-dashboard",
    "page": 1,
    "layout_page": "sales-dashboard-page",
    "path": "/work/dist/screenshots/reportartefact-sales-dashboard-001.png",
    "width": 1024,
    "height": 768,
    "layout_state": "/work/dist/screenshots/reportartefact-sales-dashboard.layout.json"
  },
  {
    "ref": "ChartStructure/revenue_chart",
    "path": "/work/dist/screenshots/chartstructure-revenue_chart.png",
    "width": 512,
    "height": 306
  }
]
```

`width` and `height` are in pixels, so they double with `--screenshot-scale 2`. PNGs from
`ScreenshotArtefact` manifests are listed here too, with their `artefact` name.

```bash
bino build --screenshot ReportArtefact/monthly --build-log-format json
bino build --screenshot overview --screenshot ChartStructure/revenue --screenshot-scale 2
```

## Overlay

`--overlay <dir>` builds a draft without saving it in the project. Each file in `<dir>` replaces
the project file at the same relative path, and a file the project does not have is added. This
holds for every kind of file: manifests, SQL files, CSV files, images.

```bash
# /tmp/draft/pages/sales.yaml replaces pages/sales.yaml,
# /tmp/draft/datasets/forecast.yaml is a new DataSet
bino build --overlay /tmp/draft --out-dir /tmp/draft-out
```

- Nothing is written to the project, so the project can be read-only. Pass an `--out-dir` outside
  the project in that case.
- `<dir>` can be anywhere, also outside the project.
- A relative path in a manifest (a CSV file, an image) resolves against the project, as without
  `--overlay`. When `<dir>` has a file at that path, that file is read instead. A path that leaves
  the project (`../shared/data.csv`) is not supported with `--overlay`.
- `bino.toml` is always read from the project. An overlay with a `bino.toml` fails the build, and
  so does an overlay file below a directory that is a link in the project.
- Lint, the layout state and all other flags work as usual.
- A file from the overlay that does not parse or validate fails the build like a project file. The
  error names the path in the project, as if the file were there, with its line, and a second line
  says that the content came from the overlay. With `--log-format json`, the error line has
  `file` (the path in the project) and `overlay` (the file that was read).

## Number values

`--number-values` writes `<artefact>.values.json` next to each report PDF (`report.pdf` gives
`report.values.json`). It lists, for every table and chart, the numbers it shows as data, so a
program or an agent can check them without reading the PDF.

```json
{
  "version": 1,
  "components": [
    {
      "id": "bn-table[0]",
      "kind": "Table",
      "name": "regions",
      "page": 1,
      "pageName": "sales_page",
      "datasets": ["sales_region"],
      "measureScale": "_",
      "measureUnit": "kEUR",
      "values": [
        { "key": "ac1", "point": { "category": "North" }, "value": 4943.583, "text": "4,944" },
        { "key": "drac1_pl1_pos", "point": { "category": "North" }, "value": 0.0047932926829267536, "text": "+0.48%" },
        { "key": "ac1", "point": { "row": "total" }, "value": 23495.97, "text": "23,496" }
      ]
    },
    {
      "id": "bn-chart-time[0]",
      "kind": "ChartTime",
      "page": 1,
      "pageName": "sales_page",
      "datasets": ["sales_monthly"],
      "measureScale": "_",
      "measureUnit": "kEUR",
      "values": [
        { "key": "ac1", "point": { "date": "2025-01-01" }, "value": 1199, "text": "1,199.0" },
        { "key": "pl1", "point": { "date": "2025-01-01" }, "value": 1208 }
      ]
    }
  ]
}
```

| Field | Meaning |
| --- | --- |
| `id` | The component id of the rendering engine, the same as in the [layout state](/cli/layout-state/). |
| `kind`, `name`, `ref` | The manifest kind, the child's `metadata.name` and its `ref`, when known. |
| `page`, `pageName` | The 1-based `LayoutPage` of the report and its name. |
| `datasets` | The DataSets the component reads. |
| `measureScale`, `measureUnit` | As set on the component. `text` is scaled by `measureScale`, `value` is not. |
| `values[].key` | The column: a scenario slot (`ac1`, `pl1`, ...) or a variance (`dac1_pl1_pos`, `drac1_pl1_pos`). |
| `values[].point` | The data point: `category`, `subCategory`, `rowGroup`, `date` (the start of the period, `YYYY-MM-DD`), and `row` (`subtotal`, `total`) for sum rows. `part: "total"` marks the total of a stack. |
| `values[].value` | The raw number the engine computed. A relative variance is a fraction (`0.05` is 5%). |
| `values[].text` | What is printed: scaled, rounded and formatted for the locale. Missing when the value has no label, like a bar without one. |

A bar and its label are one value: the bar gives `value`, the label gives `text`. Numbers come from
tables and charts only; a number written in a `Text` is not listed. The data points come from a recent
rendering engine. With an older `engine-version`, values have no `point` and cannot be checked.

With `--build-log-format json`, each artefact names the file in `values`, next to `layout_state`
(with `--layout-state`).

## Checking the numbers

`--verify-numbers` also compares each value with the rows of the component's DataSet and adds the
result to the values file:

```json
"check": {
  "values": 60,
  "matched": 57,
  "unmatched": 2,
  "differences": 1,
  "unmatchedReasons": { "no DataSet row for the data point": 2 }
},
"differences": [
  {
    "component": "bn-table[0]",
    "key": "ac1",
    "point": { "category": "North" },
    "shown": 4943.5,
    "text": "4,944",
    "expected": 5000,
    "reason": "sum of ac1 over 1 DataSet row(s)"
  }
]
```

- A scenario slot is expected to be the sum of that column over the rows with the same data point.
  A `date` matches the period of the chart's date interval, so a row dated `2025-01-31` belongs to
  the point `2025-01-01` of a monthly chart. A `total` row sums all rows, a `subtotal` row the rows
  of its `rowGroup`.
- A variance is computed from the two sums like the engine does it: `a - b` for `d...`,
  `(a - b) / |b|` for `dr...`. When `b` is 0 the engine shows `n/a`, and so the check expects no value.
- The raw `value` is compared, with a small tolerance for float rounding. `text` is only for
  information.
- A value that cannot be compared is counted as `unmatched`, not as a difference, with the reason
  in `unmatchedReasons`: no row for the point (for example an "other" category), a component with a
  `filter` or with more than one DataSet, rows with `operation: "-"`, a row whose date cannot be
  read, a value without a data point, or two values with the same data point.
- `differences` is always present with `--verify-numbers`; an empty list means nothing differs.

Differences do not fail the build. They are reported as one build warning per artefact, and the
JSON build log has the counts in `number_check`:

```json
"artefacts": [
  {
    "name": "sales_report",
    "pdf": "/work/dist/sales_report.pdf",
    "values": "/work/dist/sales_report.values.json",
    "number_check": { "values": 60, "matched": 57, "unmatched": 2, "differences": 1 }
  }
]
```

`--overlay`, `--number-values` and `--verify-numbers` cannot be combined with `--stateless`.

## Default Arguments via bino.toml

You can set default values for build flags in your project's `bino.toml` file. These defaults are applied automatically and can be overridden by explicit command-line flags:

```toml
[build.args]
out-dir = "output"
log-sql = true
no-lint = false
artefact = ["monthly", "weekly"]
exclude-artefact = ["draft"]
```

When you override a TOML default, the CLI logs an info message:

```bash
$ bino build --out-dir reports
Overriding out-dir from bino.toml ("output" -> "reports")
```

## Environment Variables via bino.toml

You can also set environment variables for builds in your `bino.toml`. This is useful for configuring query limits or connection strings:

```toml
[build.env]
BNR_MAX_QUERY_ROWS = "100000"
BNR_MAX_QUERY_DURATION_MS = "120000"
DATABASE_URL = "postgres://prod-server/reports"
```

Actual environment variables always take precedence over TOML values. When an env var overrides a TOML value, the CLI logs a message:

```bash
$ BNR_MAX_QUERY_ROWS=200000 bino build
Environment variable BNR_MAX_QUERY_ROWS overrides bino.toml ("100000" -> "200000")
```

See [bino init](/cli/init/#the-binotoml-configuration-file) for the full configuration reference.

## Examples

Build all reports in the current directory:

```bash
bino build
```

Build only selected artefacts:

```bash
bino build --artefact monthly_sales --artefact annual_sales
```

Change the output directory and log SQL:

```bash
bino build --out-dir dist/reports --log-sql
```

## Data Validation

bino can validate query results against the [DataSet schema](/reference/dataset/#standard-dataset-schema) to catch data structure issues early. Validation checks include:

- **Type validation**: Ensures fields like `category` are strings and `ac1` are numbers.
- **Enum validation**: Verifies `operation` is `"+"` or `"-"`.
- **Date format**: Checks `date` fields are ISO 8601 format (`YYYY-MM-DD`).
- **Dependent required**: Ensures paired fields are present (e.g., `rowGroup` requires `rowGroupIndex`).

Validation modes:

- `--data-validation=warn` (default) - log validation warnings and continue building.
- `--data-validation=fail` - treat validation errors as fatal and exit with code 1.
- `--data-validation=off` - skip data validation entirely.

### Checks that ignore the mode

A DataSet with [`derive` or `assert`](/reference/dataset/#deriving-previous-period) is checked on every row, not the sample, and four of those checks fail the build in every mode, including the default `warn`:

- a derived slot that the query already returns (`slot pp2 is already in the query result; use assert: for a supplied slot`),
- a missing `from` slot or `date` column,
- duplicate rows for one identity in a period,
- an `assert` mismatch against the shifted value.

A derived slot that is `NULL` on every row is a normal warning. `--warn-on-query-errors` downgrades the four errors like any other query failure.

For efficiency, only the first rows are validated (default: 10). Configure via `BNR_DATA_VALIDATION_SAMPLE_SIZE`:

```bash
BNR_DATA_VALIDATION_SAMPLE_SIZE=100 bino build
```

## CI tips

- Use `--work-dir` to point at the repository checkout.
- Fail builds early by ensuring environment variables for secrets are set.
- Archive the `dist/` directory as a build artefact.
- Set consistent build options in `bino.toml` to ensure reproducible CI builds.
- Use `--data-validation=fail` in CI to catch data issues before reports reach production.
