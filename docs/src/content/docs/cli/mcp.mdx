---
title: bino mcp
description: Run a Model Context Protocol server so AI agents can introspect, validate, author, and build reports.
---

`bino mcp` runs a [Model Context Protocol](https://modelcontextprotocol.io) server over
stdio, exposing bino's introspection, validation, authoring, and build surface to AI agent
clients such as Claude Code, Claude Desktop, and Cursor.

Because a bino report is plain-text YAML + SQL, an agent can author it directly - and bino's
schema and validation become the guardrails that tell the agent precisely whether what it
wrote is correct.

## Usage

```bash
bino mcp [--work-dir DIR]
```

Most agent clients are configured with a _command_, so `bino mcp` is the entrypoint you
register once. Under the hood:

- **Proxy mode** - if a `bino daemon` is already running for the project (for example because
  VS Code is open), `bino mcp` connects to that daemon's `/mcp` endpoint and forwards to it, so
  the agent reuses the daemon's already-loaded DuckDB session and file watcher instead of
  starting a second one.
- **Standalone mode** - with no daemon running, `bino mcp` loads the project itself and serves
  the MCP directly.

Flags:

- `--work-dir`, `-w` - report bundle directory (default: `.`).
- `--no-proxy` - always run standalone, even if a daemon is running.
- `--allow-publish` - also expose the `registry_publish` tool (see [Security](#security)). When
  `bino mcp` proxies to a running daemon, the daemon's `--mcp-allow-publish` flag decides instead.
- `--read-only` - serve only the tools that change nothing (see [Read-only mode](#read-only-mode)).
  A read-only server never proxies to a daemon.
- `--list-tools` - print the tools this server would offer and exit, without opening the project.
  It honours `--read-only` and `--allow-publish`. Add `--json` for each tool's name, title,
  annotations and input schema, so another program can check what an installed bino offers.

Every tool has a `title` and the hints `readOnlyHint` or `destructiveHint`, so a client can
decide when to ask the user before a call.

Clients that speak MCP over HTTP can instead point straight at a running daemon's endpoint,
`http://127.0.0.1:<port>/mcp`. The daemon mounts `/mcp` by default on loopback - pass
`bino daemon --mcp=false` to disable it. VS Code finds this endpoint by itself (see the
[VS Code extension](/getting-started/vscode-extension/#mcp-server)).

### The daemon port file

A running daemon writes `.bino/daemon.json` in the project root:

```json
{
  "pid": 12345,
  "port": 35425,
  "startedAt": "2026-11-24T09:00:00Z",
  "version": "0.117.0",
  "token": "3f9c..."
}
```

Every request to the daemon, `/mcp` included, must send the token as a header:
`Authorization: Bearer <token>`. Requests without it get `401`. Requests that carry an `Origin`
header (a web page) get `403`. The daemon makes a new token each time it starts, and only your
user can read the file. So configure an HTTP client with values read from the file at start:

```bash
PORT=$(jq -r .port .bino/daemon.json)
TOKEN=$(jq -r .token .bino/daemon.json)
claude mcp add --transport http bino "http://127.0.0.1:$PORT/mcp" \
  --header "Authorization: Bearer $TOKEN"
```

The port and the token change when the daemon restarts, so a client with a fixed URL must be
configured again. `bino mcp` reads the file itself on every start and has no such problem.

## Configure your client

### Claude Code

```bash
claude mcp add bino -- bino mcp --work-dir /path/to/report
```

### Claude Desktop / Cursor

Add an entry to the client's MCP config (Claude Desktop:
`claude_desktop_config.json`; Cursor: `.cursor/mcp.json`):

```json
{
  "mcpServers": {
    "bino": {
      "command": "bino",
      "args": ["mcp", "--work-dir", "/path/to/report"]
    }
  }
}
```

## Resources

Read-only context an agent can pull in:

| URI                    | Contents                                                                                                     |
| ---------------------- | ------------------------------------------------------------------------------------------------------------ |
| `bino://schema`        | The full merged JSON Schema for all manifest kinds (built-in + plugin).                                      |
| `bino://schema/{kind}` | The self-contained spec schema for one kind (e.g. `bino://schema/Table`).                                    |
| `bino://kinds`         | Every manifest kind and its capability category (`data` / `layout` / `embeddable` / `artefact` / `config`).  |
| `bino://documents`     | The project index: every document → `{kind, name, file, position}`.                                          |
| `bino://packages`      | The project's registry packages: `bino.lock` merged with `bino.toml` `[dependencies]`, with installed state. |
| `bino://templates`     | The built-in and curated templates `init_bundle` can scaffold from.                                          |
| `skill://{name}/SKILL.md` | One knowledge skill (e.g. `skill://bino-ibcs/SKILL.md`); its other files sit beside it, such as `skill://bino-ibcs/references/ibcs-standard.md`. |

## Skills

The knowledge skills below are served with the MCP
[Skills extension](https://modelcontextprotocol.io/extensions/skills/overview)
(`io.modelcontextprotocol/skills`). The server declares it in its capabilities and answers
`skills/list` (every skill with its frontmatter and the digest and size of each file) and
`skills/get` (one skill by the URI of its `SKILL.md`). Every file is also an ordinary resource
under `skill://`, so a client without the extension reads them with `resources/read`.

`bino mcp --list-skills` prints the served skills; with `--json` it prints each skill with its
frontmatter and every file with its URI, digest, size and text, so another program can serve
the same skills without running bino.

## Prompts

The server also serves bino's authoring and IBCS knowledge as MCP prompts. They are the same skills
the Claude Code plugin ships, embedded in the binary, so any client that can run `bino mcp` gets
them without a copy of the plugin. Each prompt takes no arguments and returns one user message with
the skill text, its reference files appended; the same skill is served under `skill://{name}/`.

| Prompt                 | What it teaches                                                                                                                                                                                          |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `bino-concepts`        | bino's mental model: the manifest envelope, the DataSource → DataSet → LayoutPage → artefact pipeline, dependencies, standard columns, params, constraints, `bino.toml`. Read first.                     |
| `bino-authoring`       | The authoring loop through this server: outline, scaffold, learn columns, draft, `validate_draft`, write, `validate_project`, build.                                                                     |
| `bino-ibcs`            | The IBCS rubric: SUCCESS rules, scenarios (`ac`/`pp`/`fc`/`pl`), variances, notations, choosing a component, data-aware commentary. Includes the full IBCS standard reference and the engine data model. |
| `bino-data-modeling`   | Mapping raw source columns onto scenario slots, deriving variances, choosing the grain, writing typed DataSet SQL.                                                                                       |
| `bino-validation-loop` | The four-layer check (schema, IBCS, build-readiness, acceptance) and the bounded fix loop.                                                                                                               |
| `bino-packaging`       | Authoring a registry package: the `[package]` table, naming and forbidden kinds, params, `mocks/`, `registry_publish_check`, choosing the bump, and handing the publish to the human.                    |

The plugin's `bino-orchestration` and `bino-requirements` skills are not served: they drive Claude
Code specific machinery (subagents, questions to the human) and mean nothing to other clients.

## Tools

### Understand & inspect

| Tool                                             | What it does                                                                                                                                                                                  |
| ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `list_kinds`                                     | Every manifest kind with its capability category.                                                                                                                                             |
| `outline_kind(kind)`                             | A compact outline of one kind's spec: every field with its path, type, required flag, enum, default and description. Layout kinds report the allowed child kinds as `childKinds`. Start here. |
| `scaffold_kind(kind)`                            | A minimal YAML document for one kind with every required spec field pre-filled.                                                                                                               |
| `describe_kind(kind)`                            | The full spec JSON Schema for one kind. Large (up to ~20k tokens for layout kinds); prefer `outline_kind`.                                                                                    |
| `describe_project()`                             | All documents in the project.                                                                                                                                                                 |
| `describe_document(file)`                        | The documents declared in one file.                                                                                                                                                           |
| `get_columns(name)`                              | Column names of a DataSet or DataSource (prefix `$` to force a DataSource).                                                                                                                   |
| `get_rows(name, limit?)`                         | A sample of rows from a DataSet or DataSource.                                                                                                                                                |
| `query_data(sql, limit?)`                        | Run one SELECT over the DataSources and DataSets by name, for example an aggregation, without saving a DataSet. Returns columns with DuckDB types, rows and `truncated`. `limit` defaults to 100, at most 1000. See [Querying data](#querying-data). |
| `profile_data(name, sample_rows?)`               | What the data looks like: row count; per column type, min, max, approximate distinct count and null count; the top 5 values of columns with few distinct values; for date columns the range, the step (`day`, `weekday`, `week`, `month`, `quarter`, `year`) and the missing periods; `warnings`. Above `sample_rows` rows (default 100000) the column statistics use a random sample. |
| `graph_deps(kind, name, direction?, max_depth?)` | Dependencies (`out`), dependents (`in`), or `both`. Component nodes carry a `columns` list (`dataset`, `column`, `role`, `field`) of the dataset columns they read.                           |

#### Querying data

`query_data` reads the project's DataSources by name, as the views the build creates, and DataSets
by name, compiled like the build compiles them. A DataSet is compiled only when the SQL names it.
SQL names are case-insensitive, so when a DataSet and a DataSource share a name, the name means the
DataSource. Columns from a DataSet's `constants` are not part of its rows here. A DataSet whose own
SQL reads a file or URL directly (`read_csv(...)`, `'file.csv'`) instead of through a DataSource
is not supported by `query_data` and `profile_data`: DuckDB refuses the file with a Permission
Error and the tool says why.

Each call runs on a DuckDB session of its own, never on the session the other tools share:

- The SQL must be exactly one `SELECT`. Every other statement (`INSERT`, `COPY`, `ATTACH`,
  `CREATE`, `SET`, `PRAGMA`, ...), and more than one statement, is refused.
- Table functions (`read_csv`, `read_text`, `glob`, `duckdb_secrets`, ...), `DESCRIBE`,
  `SUMMARIZE`, `SHOW`, qualified names and every table that is not a DataSource or DataSet are
  refused.
- CTE names must be plain identifiers (letters, digits, underscores).
- DuckDB's plan for the SQL may read through no function (file reader, catalog function) that
  the DataSources and DataSets it names do not read through themselves.
- The session reads only the files the DataSources read, plus the directories and URL prefixes
  of directory, glob and URL DataSources. It loads no extension, runs each statement for at most
  30 seconds, and uses at most 1 GB of memory, 1 GB of spill space and 2 threads. The settings
  are locked before the SQL runs. At most two of these calls run at the same time; the others
  wait.
- Functions that build a value whose size an argument sets are refused, whatever the
  arguments: `repeat`, `range`, `generate_series`, `list_resize`, `array_resize`, `lpad`, `rpad`,
  `printf`, `format` and `sprintf`. So are lambda functions and list comprehensions
  (`list_transform`, `list_apply`, `apply`, `list_filter`, `filter`, `list_reduce`, `reduce`,
  their `array_` forms, `x -> ...` and `[x FOR x IN ...]`).
- A cell whose JSON is larger than 4 KiB is cut and ends in `...[truncated]`. At most 200 columns
  are returned. Rows stop once the result holds more than 2 MiB of JSON, with `truncated` set;
  the remaining cells of the last row are cut. `notes` says when any of this happened.

DuckDB's memory limit covers its buffer pool, but not every value a scalar function builds, and
DuckDB cannot always interrupt one such function. The refused functions above remove the common
ways to build such values, not every one. The real backstop is an operating system memory limit:
a host that runs the daemon for others must give the process one (for example a container or
cgroup limit), so that one query cannot exhaust the machine.

An error returns DuckDB's own message, for example `Binder Error: Referenced column "x" not found`.
`profile_data` runs on such a session too.

#### Duplicate names

A project can define a DataSource, DataSet or ConnectionSecret more than once under one name and let
constraints pick one per artefact, for example synthetic data for local work and real data only in
CI. `get_rows`, `get_columns` and `validate_project(execute_queries)` resolve such a name like the
build does: they evaluate the constraints against every ReportArtefact in `preview` mode and use the
one definition all artefacts select. The result's `file` field names the manifest that answered. If
the artefacts select different definitions, or none, the tools return an error that names every
candidate instead of guessing.

### Validate

| Tool                                      | What it does                                                                                        |
| ----------------------------------------- | --------------------------------------------------------------------------------------------------- |
| `validate_project(execute_queries?)`      | Validate the project on disk; optionally execute datasets for data-validation warnings.             |
| `validate_draft(yaml)`                    | Validate manifest YAML **in memory** (no disk write) - the pre-write guardrail.                     |

### Author

| Tool                                                                 | What it does                                                                                                                                                                     |
| -------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `create_manifest(kind, name, spec, ...)`                             | Create any manifest from a spec object; validated and written atomically, auto-placed by project convention.                                                                     |
| `write_manifest(file, yaml, append?)`                                | Persist a full manifest document, validated before writing.                                                                                                                      |
| `edit_manifest(file, position, patch)`                               | Edit one document in place via dotted-path edits, preserving comments and key order.                                                                                             |
| `remove_manifest_fields(file, position, paths, dryRun?)`             | Delete dotted paths from one document in place; a trailing `[index]` removes a sequence element. Validated before the atomic write; `dryRun` returns the rewritten file instead. |
| `reorder_manifest_sequence(file, position, path, from, to, dryRun?)` | Move an element within a sequence (e.g. `spec.columns`) from one 0-based index to another, in place and validated.                                                               |
| `scaffold_source(dataSource, dataSet?)`                              | Scaffold a DataSource and an optional typed DataSet in one step.                                                                                                                 |
| `init_bundle(...)`                                                   | Bootstrap a new starter report bundle.                                                                                                                                           |

Every write validates against the merged JSON Schema before persisting, so an agent cannot
write a structurally invalid manifest. Writes are atomic (temp file + rename).

### Preview

| Tool                                        | What it does                                                                                                                                                                                                                                                                                                                                                                         |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `preview_server_start(name?, kind?, port?)` | Start `bino preview --no-open` for the project, or reuse the preview this server started, and wait for the first render. A preview started elsewhere on the same port is not reused; pass another `port`. Returns `url`; with `name`, also `embedding_url`: that one component, LayoutPage or artefact without the preview UI. Under a daemon the preview is shared with the editor. |
| `preview_server_stop()`                     | Stop the preview server.                                                                                                                                                                                                                                                                                                                                                             |

The server cannot display a page. The URL is loopback on the machine that runs bino, so only a
browser on that machine can load it. An agent that controls such a browser (for example the
built-in browser in a local Claude desktop session) opens the URL there; otherwise it hands the URL
to the human.

## The authoring loop

```text
1. outline_kind({kind:"Table"})       → the Table spec fields, types, enums, defaults
2. scaffold_kind({kind:"Table"})      → a minimal Table document to fill in
3. get_columns({name:"sales"})        → {columns:["region","ac1","pl1",...]}
4. draft the Table manifest using those columns
5. validate_draft({yaml:"..."})       → {valid:false, diagnostics:[{message:"...", ...}]}
6. fix and re-validate                → {valid:true}
7. create_manifest({kind:"Table", name:"q3", spec:{...}})
8. build({artefacts:["q3"]})          → q3.pdf
```

## Read-only mode

`bino daemon --read-only` (and `bino mcp --read-only`) is for a host that runs bino next to a
project it mounts read-only, for example a container in a hosted service. In this mode:

- Only tools that change nothing are served: `list_kinds`, `describe_kind`, `outline_kind`,
  `scaffold_kind`, `describe_project`, `describe_document`, `validate_project`, `validate_draft`,
  `get_columns`, `get_rows`, `query_data`, `profile_data` and `graph_deps`, plus the resources and
  skills.
- The authoring, registry, `build`, `get_layout_state`, publish, preview and `introspect_source`
  tools are not registered. The daemon answers its `/build`, `/preview/*`, `/registry/*` and
  `/introspect-draft` routes with `403`.
- The daemon writes no port file. Scratch files go to `$TMPDIR`, never to the project.
- The daemon does not stop by itself when it has been idle for five minutes, as an editor's
  daemon does: the program that started it decides when it stops.
- The daemon takes its token from the `BINO_DAEMON_TOKEN` environment variable, which is
  required in this mode.

```bash
BINO_DAEMON_TOKEN=... bino daemon -w /work --read-only --listen-addr 0.0.0.0 --port 8080
```

`BINO_DAEMON_TOKEN` also works without `--read-only`: the daemon then uses it instead of making a
new token, and still writes it to the port file.

## Security

The authoring tools only read and write files inside the project root. They refuse an absolute
path elsewhere, a `..` path that leaves the root, and a symlink that points out of it.

The server runs SQL, reads the filesystem, and (via `build`) launches headless Chrome. This is
intended for **local** use over stdio and a loopback HTTP endpoint. The daemon accepts only
requests with the token from its port file, rejects browser requests (any `Origin` header) and,
on loopback, any `Host` that is not a loopback name. Exposing the daemon on a
non-loopback address (`bino daemon --listen-addr`) is out of scope for this surface and would
require additional hardening.

`preview_server_start` starts a loopback HTTP server (no token, and it includes the preview's SQL
explorer) that runs until `preview_server_stop`, or until the MCP server or daemon exits.

`registry_publish` is **off by default**. It is only registered when a human starts the server with
`bino mcp --allow-publish`, or `bino daemon --mcp-allow-publish` when `bino mcp` proxies to a running
daemon. Publishing is irreversible - it mints an immutable version that cannot be deleted - and a
first publish with `visibility: public` makes the package public, so an agent must not be able to
trigger it by accident. `registry_publish_check` is always available: it uploads the package files
to the registry for validation but mints nothing. The other registry tools only change the local
project. None of them returns a credential; when `registry_auth_status` reports none, the human
runs `bino registry login`.
