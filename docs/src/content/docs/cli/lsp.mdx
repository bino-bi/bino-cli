---
title: bino lsp
description: Run a Language Server so any editor gets context-aware completion, hover, navigation, and live diagnostics for bino manifests.
---

`bino lsp` runs a [Language Server Protocol](https://microsoft.github.io/language-server-protocol/)
server over stdio. Any LSP-capable editor - VS Code, Neovim, Helix, … - connects to it and gets
**context-aware** completion, hover, navigation, rename, and live diagnostics, computed
server-side over a YAML syntax tree (not regex over text).

The same Go core that powers `bino daemon` and `bino mcp` answers the editor, so every editor
sees identical intelligence: the live merged schema (built-in + plugin kinds), the canonical IBCS
scenario/variance model, real dataset columns, and the project's validation.

## Usage

```bash
bino lsp [--work-dir DIR] [--no-proxy] [--socket PORT]
```

Editors are configured with a _command_, so `bino lsp` is the entrypoint you register once.
Under the hood it follows `bino mcp`:

- **Proxy mode** - if a `bino daemon` is already running for the project (for example because
  VS Code is open), `bino lsp` delegates the heavy data work (columns, the index, the dependency
  graph, validation) to that daemon over loopback HTTP, so the editor reuses the daemon's
  already-loaded DuckDB session and file watcher instead of starting a second one. The lightweight
  document/position session always stays local to `bino lsp`.
- **Standalone mode** - with no daemon running, `bino lsp` loads the project itself and serves
  everything in-process.

Flags:

- `--work-dir`, `-w` - report bundle directory (default: `.`).
- `--no-proxy` - always run standalone, even if a daemon is running.
- `--socket PORT` - serve over a TCP socket instead of stdio (debugging).
- `--phase2` - advertise navigation/refactor capabilities (default: on).

## Editor features

The server answers only for bino buffers. Other YAML files the editor sends (CI, Compose,
Kubernetes) get no completion, hover or diagnostics. A project's `bino.toml` is handled too, see
below.

**Completion** - IBCS scenario slots (`ac1-4 / pp1-4 / fc1-4 / pl1-4`) filtered to the columns the
bound dataset actually emits, a guided builder for the variance grammar
`d{base}_{compare}_{pos|neg|neu|op|opinv}`, the live `kind:` list, schema-driven fields and enum values,
references (`dataset:`, `ref:`, `source:`, `layoutPages:`, `selectedStyle:`, …) valid at that position, and,
inside a DataSet `query:` / `prql:` block, the upstream source's column names, DuckDB keywords and
functions, and DataSet and DataSource names after `FROM` / `JOIN`.

**Hover** - a dataset reference (also a name after `FROM` / `JOIN` in a query) shows its columns with
their types and the first rows; a field shows its schema description; a scenario or variance token
shows its IBCS meaning. Column lists and samples are cached until the project changes.

**Live diagnostics** - schema and engine-constraint errors squiggled as you type on the buffer
you're editing; lint findings, missing `${VAR}` environment variables, and engine-compat warnings
for the whole project, refreshed whenever a file changes on disk (for example on save) - all with
precise line/column, even for files you don't currently have open. Optionally (off by default), on
save each inline SQL DataSet query runs with `LIMIT 0`, and DuckDB parse and bind errors show on the
query line. This reads no rows, but it may open remote sources.

**Navigation & refactor** - Go to Definition / Find All References / Go to Implementation across the
project (also from a name after `FROM` / `JOIN` in a query), project-wide Rename of a DataSet / DataSource / component (and every reference, including its name in the SQL of DataSets that read it), document
outline and workspace symbol search, and quick-fixes: add a missing `${VAR}` to `.env`, insert a
missing required field, add a DataSource the query reads to `spec.dependencies`, or scaffold the
manifest a dangling reference points to.

**Inlay hints** - after each `${NAME}`, the value it resolves to: a param default of the document,
the environment, or `bino.toml` `[build.env]`, in the order the build reads them. Unset names get
no hint, and values of secret-looking names are masked.

**Document links** - file paths in `$file`, `localPath`, `path`, `file` and `stylesheet` link to
the file, resolved against the manifest's folder. Only existing files are linked.

**bino.toml** - syntax errors, wrong value types and keys the build ignores, as you type; completion
of table names after `[` and of the keys of the current table.

### Capabilities

The server advertises full text sync, completion (trigger characters `:`, `$`, `@`, with resolve),
hover, inlay hints and document links. With `--phase2` (the default) it also advertises definition,
references, implementation, document and workspace symbols, rename (with prepare) and quick-fix
code actions.

## Custom requests

Besides the standard methods, the server answers two requests that editor integrations can use.
Clients that do not call them see no difference.

- `bino/documents` with `{ "textDocument": { "uri": "..." } }` - the bino manifests of an open
  buffer, read from its current (unsaved) text: `isBino`, the buffer `version`, and in `documents`
  per manifest its `kind`, `name`, `position` (1-based document number in the file), `range`, and
  in `blocks` the `field`, `language` and `range` of an inline DataSet `query:` or `prql:` block.
- `bino/index` - the project index: `documents` with `kind`, `name`, `file` and `position` of
  every manifest.

A client that passes `{ "indexChanged": true }` as `initializationOptions` also gets a
`bino/indexChanged` notification whenever the project index changes on disk.

`{ "queryDiagnostics": true }` in `initializationOptions` turns on the on-save query check. A
`workspace/didChangeConfiguration` with `{ "settings": { "bino": { "queryDiagnostics": false } } }`
turns it off again (or on).

## Generic editor setup

Any LSP client can launch `bino lsp` over stdio for `yaml` documents (and `bino.toml`, if you
want its checks). For Neovim
(`nvim-lspconfig`-style):

```lua
vim.lsp.start({
  name = 'bino',
  cmd = { 'bino', 'lsp' },
  root_dir = vim.fs.dirname(vim.fs.find({ 'bino.toml' }, { upward = true })[1]),
})
```

Point any other LSP client at the command `bino lsp` with the project root as the working
directory.

## VS Code

The [bino VS Code extension](/getting-started/vscode-extension/) is a thin language client: it
spawns `bino lsp --work-dir <project>` for YAML files and `bino.toml`, and (when its daemon is
enabled) makes that daemon the single heavy instance the server proxies to. It opts in to
`bino/indexChanged`, and maps the `bino.lsp.queryDiagnostics` setting to the `queryDiagnostics`
option. YAML highlighting and folding come from VS Code's built-in YAML support; the extension adds
SQL and PRQL highlighting inside `query:` / `prql:` blocks. No configuration is needed beyond
having a recent `bino` on your `PATH` (or `bino.binPath` set). In an untrusted workspace the
extension does not start the server.
