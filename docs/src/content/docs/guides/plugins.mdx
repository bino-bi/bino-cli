Plugins let you extend bino with capabilities that go beyond what YAML manifests
and SQL queries can express. A single plugin binary can provide any combination of:

## How plugins work

Plugins are standalone executables that communicate with the bino CLI over gRPC.
bino launches each plugin as a subprocess, sends an `Init` call, and then invokes
RPCs as the pipeline progresses. When the command finishes, plugins are shut down
gracefully.

This architecture means plugins can be written in any language that supports gRPC,
though the official [Plugin SDK](https://github.com/bino-bi/bino-plugin-sdk) is
for Go.

## Installing a plugin

<Steps>

1. **Build the plugin binary**

   ```bash
   cd my-bino-plugin
   go build -o bino-plugin-myplugin .
   ```

2. **Place it where bino can find it**

   bino searches for plugins in this order:

   | Priority | Location                     | Example                                        |
   | -------- | ---------------------------- | ---------------------------------------------- |
   | 1        | Explicit path in `bino.toml` | `path = "./bin/bino-plugin-myplugin"`          |
   | 2        | Project-local                | `<project>/.bino/plugins/bino-plugin-myplugin` |
   | 3        | User-global                  | `~/.bino/plugins/bino-plugin-myplugin`         |
   | 4        | System PATH                  | Any directory in `$PATH`                       |

   The binary **must** be named `bino-plugin-<name>` where `<name>` matches the
   key in `bino.toml`.

3. **Declare it in `bino.toml`**

   ```toml
   [plugins.myplugin]
   # path = ".bino/plugins/bino-plugin-myplugin"  # optional, if not on PATH
   [plugins.myplugin.config]
   region = "eu-1"
   ```

4. **Verify**

   ```bash
   bino plugin list
   ```

</Steps>

### When a plugin does not load

A plugin declared in `bino.toml` must load. If it does not (the binary is
missing, its `Init` returns an error, or it does not match the `version` pin),
`bino build`, `preview`, `serve`, `lint`, `graph` and `schema` stop with exit
code 1:

```text
plugin declared in bino.toml did not load: loading plugin "myplugin": ...
```

Editors keep working without the plugin and show this error on `bino.toml`
(code `plugin-load-failed`). `[lint] disable` does not hide it. Plugins load
once when the editor process starts. In VS Code the daemon and the language
server both hold them, so after you fix the problem reload the window
(**Developer: Reload Window**). **Bino: Restart Daemon** is not enough: the
language server keeps talking to the old daemon.
To build without a plugin, remove its `[plugins.<name>]` table.

### Platform-specific binaries

<Aside type="tip" title="Windows users">
  On Windows, plugin binaries must have the `.exe` extension. bino automatically
  appends `.exe` when searching for plugins. If you provide an explicit `path` in
  `bino.toml`, you can omit the extension - bino will try both `<path>` and
  `<path>.exe`.
</Aside>

Since plugins are native executables, you need a separate binary per
platform. The naming convention is:

| Platform      | Binary name                |
| ------------- | -------------------------- |
| macOS / Linux | `bino-plugin-myplugin`     |
| Windows       | `bino-plugin-myplugin.exe` |

On macOS, you may need to sign the binary before it can run:

```bash
codesign --force --sign - bino-plugin-myplugin
```

## Plugin configuration

Plugins receive their configuration from `bino.toml` at startup:

```toml
[plugins.salesforce]
path = ".bino/plugins/bino-plugin-salesforce"   # optional explicit path
version = "^1.2"                                 # optional semver constraint

[plugins.salesforce.config]
instance_url = "https://myorg.salesforce.com"
api_version = "58.0"
```

The `config` map is passed to the plugin's `Init` RPC as key-value pairs. The
values are passed as written: bino does not expand `${VAR}` in them. With the
Go SDK (v0.0.4 and later), the plugin reads them in its `OnInit` callback.

To keep a secret out of `bino.toml`, let the plugin read it from its
environment (for example `MY_API_KEY`). The plugin process inherits bino's
environment. Values from a `[build.env]`, `[preview.env]` or
`[serve.env]` table in `bino.toml` are part of that environment only in
`bino build`, `bino preview` and `bino serve`, and in the editor daemon, which
uses `[preview.env]`.

`version` is a semver constraint, either an exact version (`"1.2.0"`) or a
range (`">=1.0 <2.0"`, `"^1.2"`). bino checks it against the version the plugin
reports, and a plugin that does not match fails to load.

## What plugins can do

### Custom DataSources

A plugin can register new `kind` values that behave like built-in DataSources.
When bino encounters a document with a plugin-provided kind, it calls the
plugin's `CollectDataSource` RPC to fetch data.

```yaml
apiVersion: bino.bi/v1alpha1
kind: SalesforceDataSource # provided by plugin
metadata:
  name: opportunities
spec:
  object: Opportunity
  query: "SELECT Id, Name, Amount FROM Opportunity WHERE StageName = 'Closed Won'"
```

Plugins can return data as JSON rows (registered as a DuckDB view) or as a
DuckDB SQL expression (e.g., `read_parquet('s3://...')`).

### Custom Components

Plugins can ship Web Components and render custom HTML for visual kinds:

```yaml
apiVersion: bino.bi/v1alpha1
kind: ExampleChart # provided by plugin
metadata:
  name: revenue_chart
spec:
  dataset: monthly_revenue
  chartType: bar
  title: Monthly Revenue
```

The plugin generates HTML (e.g., `<bn-example-chart ...>`) and provides the
JS/CSS assets that implement the Web Component.

Each asset needs a URL path under `/plugins/<plugin-name>/`, for example
`/plugins/example/chart.js`. bino serves these paths in `bino preview`,
`bino serve`, and to the browser that renders PDFs and screenshots. Absolute
`https://` URLs are linked as they are. Any other path logs a warning and is
not served. A path under another plugin's `/plugins/` prefix is skipped, so
one plugin cannot replace another plugin's files.

bino writes the script and style tags in the order the plugin returns its
assets, plugin by plugin in load order, so a library listed before the code
that uses it also loads first. If two assets have the same path, the first one
is kept and bino logs a warning. A style whose media type is a font, an image,
or any other type that is not CSS is served but gets no `<link>` tag. A style
without a media type is linked unless its file extension marks it as a font or
an image, so an external stylesheet URL without a `.css` suffix still works.

A component kind can be used as a child of a `LayoutPage` or `LayoutCard`, as
a `Grid` cell, or as a `Tree` node, inline or by `ref` to a document of that
kind:

```yaml
apiVersion: bino.bi/v1alpha1
kind: LayoutPage
metadata:
  name: overview
spec:
  children:
    - kind: ExampleChart            # inline
      spec:
        dataset: monthly_revenue
        chartType: line
    - kind: ExampleChart            # ref, spec fields override
      ref: revenue_chart
      spec:
        title: Revenue (override)
```

The spec is validated against the plugin's schema when the project loads, for
inline children and for top-level plugin documents. A `spec.dataset` name links
the component to that dataset in the dependency graph. The `name` the plugin
receives is the `ref` if set, else `metadata.name`, else empty. Tree nodes have
no `metadata`, so they send the `ref` or nothing.

Warning and error diagnostics that a plugin returns from `RenderComponent`
appear as warnings in the `bino build` output and in the build log, prefixed
with the plugin, the kind and the name. In `bino preview` and `bino serve` they
appear only in the terminal log. Info diagnostics are logged at debug level.
Diagnostics never fail the render: to fail it, return an error.

A `DocumentArtefact` can embed a top-level plugin document with
`:ref[Kind:name]`, for example `:ref[ExampleChart:revenue_chart]`. The plugin
receives the document's `metadata.name` and spec, and the plugin assets are
added to the document `<head>`. In a document, warning and error
diagnostics and a failed render appear in the terminal log. A failed render
shows a placeholder in place of the component and does not fail the document.

### Lint rules

Plugin lint rules run alongside bino's built-in rules during `bino lint`,
`bino build`, and `bino preview` (with `--lint`):

```bash
bino lint
# ✓ Checked 12 rule(s) (including 3 plugin rules)
# ⚠ salesforce/deprecated-api-version: ...
```

### Pipeline hooks

Plugins subscribe to pipeline checkpoints:

- `post-dataset-execute` - after SQL queries run
- `post-render-html` - after HTML is generated

These are the only checkpoints bino dispatches. A plugin that subscribes to any
other checkpoint gets a warning when it loads.

Hooks can inspect and modify the pipeline payload (e.g., transform HTML,
validate datasets, collect metrics).

### CLI commands

Plugins can add subcommands to bino:

```bash
bino plugin exec salesforce:auth --instance https://myorg.salesforce.com
bino plugin exec salesforce:sync --object Account
```

### Host access (bidirectional)

Plugin callbacks can query the host's state:

- **QueryDuckDB** - run SQL against the executed DataSets
- **GetDocument** - fetch a specific manifest document
- **GetDatasetResult** - retrieve pre-computed dataset results
- **ListDocuments** - list all loaded documents

`QueryDuckDB` runs each query in a throwaway DuckDB session. The session holds
one view per executed DataSet of the artefact being rendered, named by its
`metadata.name`. DataSources are not visible. DataSets are available from the
`post-dataset-execute` hook onward, so in `RenderComponent` and in later hooks.
Before that hook, for example in `CollectDataSource`, `bino build` shows no
DataSets, but `bino preview` and `bino serve` can still show the DataSets of
the previous render. In `bino preview`, an embed or presentation render that
runs at the same time can also replace the DataSets at any point, so a query
can see another artefact's DataSets. `QueryDuckDB` is not available in
`bino lint` or the language server. Nothing a query changes is kept: a
`DROP VIEW` or `CREATE TABLE` ends with the session. A DataSet that cannot be
loaded as a view is skipped with a warning diagnostic, and the query still runs.
A failing query returns an error diagnostic.

This enables data-aware plugins that make decisions based on the current
report's data and configuration.

## Building a plugin

See the [Plugin SDK documentation](https://github.com/bino-bi/bino-plugin-sdk)
for a complete guide to building plugins with Go, including the API
reference.

A minimal plugin looks like:

```go
package main

import sdk "github.com/bino-bi/bino-plugin-sdk"

func main() {
    sdk.Serve(&sdk.PluginOpts{
        Name:    "myplugin",
        Version: "0.1.0",
        // ... register capabilities
    })
}
```

## Limitations

- **No marketplace**: Plugins are distributed manually. Copy the binary to the
  project or install it on PATH.
- **No automatic updates**: bino does not install or update plugins. A
  `version` pin only checks the binary you installed.
- **Platform-specific**: Each target OS/architecture needs its own binary.
- **Early access**: The plugin API may change between bino releases. Pin your
  SDK dependency to a specific version.
